# 指令库模型训练：异步闭环、状态与进度、HF 缓存与 base_model 占位名

本文档汇总**同一需求迭代内**就「训练」相关的**三轮问题**及最终解决方案（与 **D039** 重叠部分以 D041 为收口说明）。

---

## 第一轮：训练成功信号、下载与「仅拉长超时」

### 现象
- 仅把 axios 超时拉到约 2 分钟，**不能**形成「训练完成 → 前端感知 → 可下载」的闭环。
- `GET .../models/{id}/download` 曾返回 **JSON**（`package_uri` 等），前端用 Blob 保存**并非真实 zip**。

### 期望
- 提交训练后 HTTP **尽快返回**；训练在后台执行。
- 前端在 **trained / failed** 时得到明确提示，而非仅「已提交」。
- 下载为**真实模型包文件**（zip）。

### 根因
- 顶层 `import trainer` 导致 **torch** 在请求路径上加载，易触发 **15s 超时**。
- **BackgroundTasks** 与 **`get_db` commit** 顺序导致后台读库仍见 **draft**（见第三轮合并说明）。
- 下载接口设计为 JSON，与「文件下载」语义不符。

### 解决方案
- 路由内 **`_run_training_background` 延迟 import** `execute_training`。
- **`POST /train`（及 evaluate）在 `add_task` 前 `await db.commit()`**（见下）。
- 前端 **`startTrainJob` + `pollTrainingUntilDone`**，对 **`GET /models/{model_id}`** 轮询并合并 **progress**；训练完成/失败再 `message`。
- **`GET .../download`** 使用 **`FileResponse`** 返回 **zip**；前端 **`responseType: 'blob'`**，文件名为 **`.zip`**。
- 契约/集成测试：`test_train_http_status`、`PATCH` 后台入口为 `_run_training_background`。

---

## 第二轮：状态长期 draft、进度 0%、HF 缓存位置

### 现象
- 轮询时模型状态**长期为 draft**，或训练中 **progress 一直为 0%**，不知是否在跑。
- 疑问：**tokenizer / 预训练权重**是否应「内置项目」；是否每次训练都重新下载。

### 期望
- 提交后很快可见 **training**，且 **progress** 能反映准备阶段与 epoch 阶段。
- **同一 base_model** 在本机**复用缓存**；缓存目录**位于项目内**便于备份/挂载，但 **Git 忽略**。

### 根因
- **事务未在调度后台任务前提交**，后台新会话读到旧状态（与第一轮 commit 根因相同）。
- **准备阶段**（读库、**from_pretrained**）耗时内 DB 仍为 **progress=0**；首次拉权重也可能较慢。
- 默认 **HF 缓存**常在用户目录 `~/.cache/huggingface`，**非项目路径**，易被误解为「每次重下」。

### 解决方案
- **`configure_huggingface_cache()`**（`app/core/hf_cache.py`）在 **`create_app()`** 首行执行，默认 **`HF_HOME` → `<backend>/data/hf_cache`**；**`config.HF_HOME`** 可覆盖。
- **`.gitignore`** 忽略 **`data/hf_cache/`**（含仓库根与 `backend` 侧规则）；**`data/README.md`** 说明用途与预下载命令。
- **trainer**：后台启动后 **`progress` 1 → 5（准备）→ 10（准备完成）→ epoch 回调**；准备阶段异常 **`notes` 写入具体异常**（见第三轮）。
- **Detail.jsx**：`progress === 0` 且训练中时展示 **「准备中」** 与 **Tooltip**，避免误读为卡死。
- **`prefetch_hf_cache.py`**：`snapshot_download` 预拉模型；**`--migrate-user-cache`** 将 `~/.cache/huggingface/hub` **复制**到项目 hub（不删原目录）。
- **UI**：**`ModelStatusTag`** 增加 **failed**。

## 第三轮：训练准备失败与无效 `base_model` 占位名

### 现象
- **`notes`**：`训练准备阶段失败: intent-bert-base-zh is not a local folder and is not a valid model identifier listed on 'https://huggingface.co/models' ...`
- 或其它准备阶段异常仅提示「详见服务器日志」，**难以在前端/DB 直接排查**。

### 期望
- 下拉中的 **base_model** 均为 **Hugging Face 可加载**的合法 **`model id`**。
- 非业务类准备失败时，**notes 中带出异常摘要**（截断），减少只查日志的成本。

### 根因
- 前端 **`BASE_MODEL_OPTIONS`** 曾使用 **占位名**（`intent-bert-base-zh`、`intent-mini-lm-v2`、`custom-onnx-base`），**Hub 上不存在**。
- **`TrainingPreparationError` 以外**的准备阶段异常原先把 **`notes` 固定成泛化文案**。

### 解决方案
- **Detail.jsx**：选项改为 **`bert-base-chinese`**（中文推荐）、**`distilbert-base-uncased`**（英文）、**`prajjwal1/bert-tiny`**（极小/调试）；默认 **`bert-base-chinese`**。
- **`prefetch_hf_cache.py`** 的 ID 列表与上述一致。
- **集成测试** `test_intent_library_flow` 中 `base_model` 改为 **`bert-base-chinese`**。
- **trainer**：`except Exception` 分支 **`notes` = `训练准备阶段失败: {str(e)[:8000]}`**。

---

## 复现步骤（历史问题，修复后不应再出现）

1. 第一轮：点击训练 → 仅延长超时仍无完成提示 / 下载非 zip；或列表长期 draft。
2. 第二轮：训练中进度条长期 0%；缓存不在 `backend/data/hf_cache`。
3. 第三轮：选用旧占位 `intent-bert-base-zh` 训练 → Hub 报错；或准备失败仅见泛化文案。
