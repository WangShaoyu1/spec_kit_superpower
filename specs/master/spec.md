# 功能规范: SmartChef 智能对话管理平台

**功能分支**: `master`
**创建时间**: 2026-03-03
**状态**: 草稿 → 澄清完毕（经过 8 轮头脑风暴 + clarify 校验）
**输入**: 替换讯飞旧方案，为智能微波炉（15.6寸+7寸双屏，NVIDIA Jetson Nano）构建完全自研的对话管理平台

## 项目定位

本项目是一个 **智能对话管理平台**，包含两个交付物：

1. **后台管理系统**（Web）：供产品经理配置指令、知识库、闲聊人设，进行测试和版本发布
2. **对话管理 API**（云端服务）：供智能微波炉设备端 APP 直连调用，按设备隔离会话

系统接收上游 ASR 模块输出的文本（不涉及语音识别），执行语义理解与对话管理，输出结构化指令和回复文本。替换现有讯飞方案（基于正则词法匹配，无法满足个性化需求）。

### 范围边界

- **在范围内**: 语义理解、对话状态管理、指令识别与槽位提取、知识问答、开放闲聊、联网内容、后台配置与测试、版本发布、多语言（中/英）
- **不在范围内**: ASR 语音识别（上游模块）、TTS 语音合成（下游模块）、设备端 UI 渲染（设备端 APP）、双屏路由（设备端 APP 自行决定）、离线能力（V2 规划，ASR 在线，断网无文本输入）、主动推送（V1 不做）、用户偏好域（V2 规划）

### 目标设备

智能微波炉，配备：
- NVIDIA Jetson Nano 系列处理器，剩余算力 3-5 TOPS，可用内存 1.1-1.5GB，硬盘 10GB
- 15.6 寸大屏：菜谱展示与互动
- 7 寸小屏：烹饪控制与系统设置
- 操作系统 Linux，应用框架 C++ / QT
- 约 39 个已定义功能（参见 temp_data/config.json）

## 用户场景与测试 *(必填)*

### 用户故事 1 - 指令配置管理 (优先级: P1)

产品经理在后台管理系统中，对智能微波炉的语义指令进行增删改查操作。每个指令包含意图名称、中文描述、所需槽位（实体参数）定义、槽位追问提示等。PM 可以编辑指令的提示词或训练数据，用于优化识别效果。配置完成后，指令变更纳入对话方案，等待发布。指令必须归属某个“指令库”，并由指令库承载语种（固定中文/英文）。每个指令库可管理多个小模型版本（上限 5），并在“测试态/发布态”之间受控切换。

**优先级原因**: 后台管理系统是整个平台的基础，没有指令配置就无法驱动对话管理。

**独立测试**: 可以通过 PM 在后台创建/编辑/删除一个指令，验证配置持久化和展示是否正确，独立交付指令管理能力。

**验收场景**:

1. **给定** PM 已登录后台, **当** 创建一个新指令"设置烹饪时间"并定义必填槽位 `duration`, **那么** 指令保存成功，列表中可见新指令
2. **给定** 已有指令"启动烹饪", **当** PM 编辑其提示词/训练数据, **那么** 修改保存成功，版本标记为"未发布"
3. **给定** 已有指令"调高音量", **当** PM 删除该指令, **那么** 指令从列表移除，关联的训练数据同步清理
4. **给定** PM 查看指令列表, **当** 按分类筛选"烹饪控制", **那么** 仅显示烹饪控制类指令
5. **给定** 指令库已存在多个模型版本, **当** PM 将模型 B 设为 testable, **那么** 系统自动取消模型 A 的 testable，且同库仅保留一个 testable

### 用户故事 2 - 知识库管理 (优先级: P1)

产品经理在后台管理系统中，上传文档（JSON/Markdown 格式）建立知识库。系统自动对文档内容建立索引。知识库按分类管理（菜谱知识、公司信息、产品使用指南等）。当前已有约 1000 道菜谱数据，菜谱格式包含：菜名、基本描述、食材配料（主料/辅料及用量）、烹饪步骤、营养成分、烹饪器具、分类标签等。

**优先级原因**: 知识库是知识问答能力的数据基础，且菜谱数据已就绪可直接导入。

**独立测试**: 可以通过上传一份菜谱文档，验证文档被索引并可通过问答检索到，独立交付知识库管理能力。

**验收场景**:

1. **给定** PM 已登录后台, **当** 上传一份菜谱 Markdown 文档, **那么** 系统自动解析文档内容并建立索引，PM 可在知识库列表中看到新条目
2. **给定** 已导入"柠香雪梨银耳汤"菜谱, **当** PM 在知识库中搜索"银耳汤", **那么** 能检索到该菜谱条目
3. **给定** PM 上传一份菜谱 JSON 文件（含无效字段如图片URL、点赞数等）, **当** 系统解析该文件, **那么** 自动过滤无效字段，仅保留知识问答所需的有效信息（菜名、食材、步骤、营养等）
4. **给定** PM 创建知识分类"菜谱"和"公司信息", **当** 上传不同类别的文档, **那么** 文档归入对应分类，支持按分类浏览和管理

### 用户故事 3 - 对话方案配置与测试 (优先级: P1)

产品经理创建"对话方案"——一套完整的对话管理配置，包含指令库配置、知识库引用、闲聊人设、大模型选型、路由策略等。每个方案可并行绑定多个指令库（典型为中文库 + 英文库），并配置“指令阈值”（得分 > 阈值视为命中指令，否则进入知识/闲聊链路）。PM 可以创建多个方案（如方案 A 用 GPT-4o + 活泼人设，方案 B 用千问 + 专业人设），分别进行手动单条测试，对比效果后选择最佳方案发布。小模型在各方案间按“库发布态”共享：对话方案仅消费指令库内 published 模型能力，不直接选择 testable 模型。

**优先级原因**: 对话方案是整个平台的核心抽象，连接后台配置与生产 API。

**独立测试**: 可以通过创建两个不同配置的对话方案，分别在手动测试界面发送相同问题，对比回复差异。

**验收场景**:

1. **给定** PM 已登录后台, **当** 创建对话方案"方案A"并配置大模型为 GPT-4o、人设为"活泼友好的厨房助手", **那么** 方案保存成功
2. **给定** 已有方案 A 和方案 B, **当** PM 在方案 A 的手动测试界面发送"红烧肉怎么做", **那么** 系统按方案 A 的配置（LLM + 人设 + 知识库）返回回复
3. **给定** PM 在方案 B 的手动测试界面发送相同问题, **当** 方案 B 配置了不同的大模型和人设, **那么** 回复内容和风格与方案 A 有可见差异
4. **给定** PM 选定方案 B 效果最佳, **当** 点击"发布"并确认, **那么** 方案 B 的配置打包为新版本，所有设备立即切换到新版本，现有设备会话上下文重置
5. **给定** 方案已绑定中文库与英文库, **当** 输入英文且英文库未命中指令, **那么** 系统进入知识/闲聊链路，不回退中文指令库
6. **给定** 方案绑定了指令库 X, **当** 库 X 无 published 模型, **那么** 方案发布被阻止并提示需先发布该库模型

### 用户故事 4 - 手动单条对话测试 (优先级: P1)

产品经理在后台选定一个对话方案后，进入手动测试界面——一个聊天窗口。PM 可以逐条发送消息模拟用户对话，系统实时展示完整的处理链路调试信息。每次测试创建独立的会话，会话之间相互隔离。PM 还可以模拟设备上下文（如当前正在烹饪、炉门已关闭、当前页面等）。

**优先级原因**: 手动测试是 PM 验证对话效果、调优配置的核心工具，直接影响发布质量。

**独立测试**: 可以通过在测试界面发送一条指令，验证调试面板完整展示所有链路信息。

**验收场景**:

1. **给定** PM 在方案 A 的测试界面, **当** 发送"设置温度180度", **那么** 聊天窗口显示回复文本，同时调试面板展示：路由结果（指令域 + 置信度）、意图（set_cooking_temp + 置信度）、槽位（number=180）、对话状态变化、响应耗时
2. **给定** PM 在测试界面, **当** 发送"柠香雪梨银耳汤需要哪些食材", **那么** 调试面板显示：路由结果（知识域）、命中的知识库条目（柠香雪梨银耳汤）、回复文本
3. **给定** PM 设置设备上下文为"当前正在烹饪，温度 200℃", **当** 发送"还有多久", **那么** 系统结合设备上下文理解为查询剩余烹饪时间
4. **给定** PM 在同一会话中先说"搜个红烧肉"再说"收藏它", **当** 查看对话状态, **那么** 可看到"它"被消解为上轮提到的红烧肉菜谱
5. **给定** PM 创建了两个独立的测试会话, **当** 在会话 1 中建立了对话上下文, **那么** 会话 2 不受影响，上下文完全隔离

### 用户故事 5 - 设备端指令语义理解 (优先级: P1)

终端用户通过语音对智能微波炉下达控制指令（如"开始烹饪"、"设置温度180度"、"解冻鸡胸肉"），ASR 模块将语音转为文本后，本系统接收文本及设备上下文，识别出用户的指令意图和槽位参数，返回结构化指令和确认回复文本。当必填槽位缺失时，系统自动发起多轮追问填充槽位。指令类响应延迟 < 200ms。

**优先级原因**: 指令识别是智能微波炉的核心能力，直接关系设备控制和用户安全。

**独立测试**: 可以通过 API 发送一批指令文本，验证意图识别准确率 ≥ 95%，响应延迟 < 200ms。

**验收场景**:

1. **给定** 系统已加载发布版本, **当** API 收到文本"开始烹饪"和设备上下文, **那么** 返回意图 `voice_cmd_start_cooking`、回复文本"好的，开始烹饪"，响应 < 200ms
2. **给定** 系统已加载发布版本, **当** API 收到文本"加热到180度", **那么** 返回意图 `set_cooking_temp`、槽位 `{number: 180}`、回复文本"好的，已设置温度为180度"
3. **给定** 系统已加载发布版本, **当** API 收到文本"加热一下"（缺少时间槽位）, **那么** 系统识别意图但检测到必填槽位缺失，返回追问"请问您要加热多长时间？"
4. **给定** 上一轮系统追问了加热时间, **当** 用户回答"5分钟", **那么** 系统补全槽位，返回完整指令 `set_cooking_time` + `{duration: 5分钟}` + 确认文本
5. **给定** 用户说"把火关了"/"关火"/"熄火", **当** 系统处理这些不同表达, **那么** 均识别为 `voice_cmd_stop_cooking`，准确率 ≥ 95%
6. **给定** 用户用英文说"Start cooking", **当** 系统检测到英文, **那么** 识别为 `voice_cmd_start_cooking`，英文回复"OK, cooking started"
7. **给定** 某指令库已发布模型版本, **当** PM 下载该模型产物并分别在 Python 与 C++ 推理环境加载, **那么** 两端均可完成推理调用且模型版本一致

### 用户故事 6 - 知识问答与开放闲聊 (优先级: P2)

终端用户向设备提问菜谱相关问题（"红烧肉需要哪些食材"）、公司相关问题，或进行日常闲聊（"今天天气怎么样"、"讲个笑话"）。系统先在知识库中检索匹配，命中则返回知识问答结果；未命中则走开放闲聊，由大模型生成回复。闲聊需支持联网内容查询（天气、股票、新闻等）。回复遵循 PM 配置的人设风格。响应时间 2-4s。

**优先级原因**: 知识问答和闲聊是产品差异化体验的重要组成，但优先级低于指令控制。

**独立测试**: 可以通过 API 发送菜谱问题和闲聊问题，验证知识命中率和回复质量。

**验收场景**:

1. **给定** 知识库已导入 1000 道菜谱, **当** 用户问"柠香雪梨银耳汤需要哪些食材", **那么** 系统从知识库检索到该菜谱，回复包含主料（银耳、雪梨）和辅料（枸杞、红枣、冰糖等）
2. **给定** 知识库中没有"法式鹅肝"菜谱, **当** 用户问"法式鹅肝怎么做", **那么** 系统未在知识库命中，转为开放闲聊由大模型回答
3. **给定** 用户问"今天上海天气怎么样", **当** 系统识别为需要联网查询, **那么** 调用外部搜索服务获取实时天气信息并回复
4. **给定** PM 配置人设为"活泼友好的厨房助手", **当** 用户说"讲个笑话", **那么** 回复符合人设风格，语气活泼友好
5. **给定** 用户用英文问"What ingredients do I need for steamed fish?", **当** 系统检测到英文, **那么** 用英文回复

### 用户故事 7 - 对话路由与上下文管理 (优先级: P2)

系统接收用户文本后，需先判断路由（指令/知识/闲聊），路由策略可在对话方案中配置（默认指令优先）。同时系统维护多轮对话上下文，支持指代消解（"它"、"这个"）、省略恢复（上文提到烤箱后直接说"关掉"）、跨域切换（从闲聊切到指令）。API 端维护会话状态，按设备隔离。

**优先级原因**: 路由准确性决定用户体验，上下文管理是多轮对话的基础。

**独立测试**: 可以通过构造跨域、指代、省略等多轮对话测试用例，验证路由和上下文管理的准确性。

**验收场景**:

1. **给定** 路由策略配置为"指令优先", **当** 用户说"红烧肉怎么做"（可匹配菜谱搜索指令或知识问答）, **那么** 优先匹配为菜谱搜索指令 `search_recipe_by_cuisine_type` 或 `set_foodtype`
2. **给定** 上一轮用户搜索了"红烧肉", **当** 用户说"收藏它", **那么** 系统消解"它"为上轮的红烧肉菜谱
3. **给定** 用户正在闲聊, **当** 用户突然说"暂停烹饪", **那么** 系统正确识别为跨域切换到指令域
4. **给定** 设备 A 和设备 B 同时调用 API, **当** 设备 A 建立了对话上下文, **那么** 设备 B 的会话完全独立，不受设备 A 影响
5. **给定** 后台发布了新版本, **当** 设备收到版本更新通知, **那么** 设备会话上下文立即重置，使用新版本配置

### 用户故事 8 - 批量测试与智能分析 (优先级: P3)

产品经理在后台对选定的对话方案执行批量测试。系统依据当前配置的能力，按日常用户表达自动生成测试用例（PM 可手动修改、微调）。批量执行后，系统输出测试报告，包含每条用例的预期匹配、实际匹配、得分。若未达到设定的准确率/响应时效指标，系统进行智能分析，生成问题分析报告，指出具体哪些意图/知识条目表现不佳及可能原因，供 PM 反馈调优。形成"出版本 → 测试 → 反馈 → 优化 → 再迭代"的闭环。

**优先级原因**: 批量测试是系统质量保障的关键手段，但可在核心功能稳定后再建设。

**独立测试**: 可以通过创建一个测试集并执行，验证报告生成和智能分析结果。

**验收场景**:

1. **给定** PM 选定对话方案并进入批量测试页面, **当** 点击"自动生成测试用例", **那么** 系统根据当前意图配置和知识库内容，生成覆盖各意图和知识条目的测试集
2. **给定** 自动生成的测试集有 200 条用例, **当** PM 手动修改其中 10 条（调整用例语句或预期结果）, **那么** 修改保存成功，手动调整的用例标记为"已微调"
3. **给定** PM 设定性能指标为"指令准确率 ≥ 95%、响应延迟 ≤ 200ms", **当** 执行批量测试后准确率为 91%, **那么** 系统标记为"未达标"并自动生成智能分析报告
4. **给定** 智能分析报告已生成, **当** PM 查看报告, **那么** 报告包含：总体指标汇总、各意图的准确率排名、混淆矩阵（哪些意图之间容易混淆）、失败用例归因分析（表达覆盖不足/槽位提取失败/路由错误等）、优化建议
5. **给定** PM 根据报告调整了训练数据并重新发布, **当** 再次执行批量测试, **那么** 可对比两次测试结果的变化趋势

### 用户故事 9 - 生产 API 监控与设备日志 (优先级: P2)

产品经理在后台管理系统中查看生产 API 的运行状况。系统提供完整的监控仪表盘，实时展示 API 的请求量、响应延迟、意图识别准确率、路由分布等核心指标。PM 可按设备 ID 维度查看该设备的所有历史会话和请求日志，包括每次请求的完整处理链路（输入文本、路由结果、意图/槽位、响应内容、耗时等）。当指标异常时，系统自动告警。

**优先级原因**: 章程要求每个推理请求 MUST 有完整的监控和追踪，且设备级日志对排查线上问题至关重要。

**独立测试**: 可以通过 API 发送一批请求后，在后台监控页面验证请求日志完整记录，按设备 ID 筛选可查看对应会话。

**验收场景**:

1. **给定** 生产 API 已有请求流量, **当** PM 进入监控仪表盘, **那么** 可看到实时指标：总请求量、QPS、平均延迟、P95 延迟、意图识别准确率、路由分布（指令/知识/闲聊比例）
2. **给定** PM 在仪表盘中输入某设备 ID, **当** 搜索该设备, **那么** 显示该设备的所有历史会话列表（会话ID、起止时间、轮数）
3. **给定** PM 选定某设备的某个会话, **当** 展开查看, **那么** 可看到该会话中每一轮请求的完整链路：输入文本、路由结果+置信度、意图+置信度、槽位提取详情、响应文本、处理耗时、设备上下文快照
4. **给定** PM 设定告警规则"意图识别准确率 < 90% 持续 5 分钟", **当** 线上准确率持续下降触发阈值, **那么** 系统发送告警通知
5. **给定** PM 查看请求日志列表, **当** 按时间范围、设备 ID、路由类型、意图名称等条件筛选, **那么** 可快速定位目标请求

### 用户故事 10 - 角色权限管理 (优先级: P2)

后台管理系统内置一个管理员账号，管理员可添加其他账号并分配角色和菜单权限。预计 2-3 名 PM 使用，不对接公司现有账号体系。

**优先级原因**: 权限管理是后台系统安全性的基本要求。

**独立测试**: 可以通过管理员创建一个受限角色的账号，验证该账号只能访问授权的菜单功能。

**验收场景**:

1. **给定** 系统初始化完成, **当** 使用默认管理员账号登录, **那么** 可以访问所有功能模块
2. **给定** 管理员创建账号"PM小王"并分配角色"指令编辑员"（仅有指令配置和测试权限）, **当** PM小王登录, **那么** 只能看到指令配置和测试相关菜单，无法访问知识库管理或版本发布
3. **给定** 管理员修改"PM小王"的角色权限, **当** 添加知识库管理权限, **那么** PM小王下次访问时可看到知识库管理菜单

### 边界情况

- 当输入文本为空或仅含标点符号时，API 返回错误提示而非崩溃
- 当输入文本超长（> 500 字符）时，系统截断处理并记录告警日志
- 当输入文本包含混合意图（如"关掉微波炉然后搜一下蛋糕的做法"）时，系统拆分为多个独立指令依次处理
- 当用户说的话无法匹配任何指令且知识库也未命中时，走开放闲聊兜底
- 当意图分类置信度低于阈值时，触发澄清对话而非静默回退或错误执行
- 当外部搜索服务（天气/新闻等）不可用时，回复"暂时无法获取该信息"
- 当 PM 上传的文档格式异常或内容为空时，返回明确的错误提示
- 当 PM 尝试删除已发布版本中使用的指令时，提示需先取消关联或创建新版本
- 当设备传入的上下文信息缺失时，系统仍能处理，仅在需要上下文的场景降级响应
- 当中英混杂输入（如"帮我 start cooking"）时，按中文优先处理
- 当多名 PM 同时编辑同一意图或对话方案时，采用 last-write-wins 策略（后保存覆盖先保存），不加锁（2-3 人规模冲突概率极低，简单方案优先）

## 需求 *(必填)*

### 功能需求

**后台管理系统** *(FR-001 ~ FR-016，对应 US1-US8)*

- **FR-001** [UI:user-mgmt]: 系统必须提供角色权限管理功能，内置管理员账号，支持创建账号、分配角色和菜单权限
- **FR-002** [UI:intent-library]: 系统必须支持指令的增删改查，每个指令包含：意图标识、中文描述、槽位定义（名称/类型/是否必填）、槽位追问提示
- **FR-003** [UI:intent-library]: 系统必须支持指令的提示词和训练数据编辑，PM 可调整以优化识别效果
- **FR-004** [UI:knowledge-base]: 系统必须支持知识库文档上传（JSON/Markdown 格式），自动解析内容并建立索引
- **FR-005** [UI:knowledge-base]: 系统必须自动过滤文档中的无效字段（图片URL、OSS链接、点赞数、审核状态等），仅保留知识问答所需的有效信息
- **FR-006** [UI:knowledge-base]: 系统必须支持知识库的分类管理（如菜谱、公司信息、产品指南）
- **FR-007** [UI:dialog-profile]: 系统必须支持创建和管理多个"对话方案"，每个方案可独立配置大模型选型、闲聊人设、路由策略
- **FR-008** [UI:dialog-profile]: 系统必须支持对话方案中的闲聊人设自定义（助手名称、性格特征、语气风格）
- **FR-009** [UI:dialog-profile]: 系统必须提供手动单条对话测试功能，以聊天界面形式与选定方案交互，测试会话之间相互隔离
- **FR-010** [UI:dialog-profile]: 手动测试必须展示完整调试信息：路由判断+置信度、意图分类+置信度、槽位提取详情、对话状态变化、知识库命中条目、响应耗时
- **FR-011** [UI:dialog-profile]: 手动测试必须支持模拟设备上下文（烹饪状态、炉门状态、当前温度、当前页面、屏幕信息）
- **FR-012** [UI:batch-test]: 系统必须支持批量测试功能：根据当前配置自动生成测试用例，PM 可手动修改微调
- **FR-013** [UI:batch-test]: 批量测试用例模板必须包含：用例编号、用例语句、预期路由、预期意图、预期槽位、实际路由、实际意图、实际槽位、匹配得分、响应耗时、是否达标
- **FR-014** [UI:batch-test]: 批量测试未达标时，系统必须生成智能分析报告，包含：总体指标汇总、各意图准确率排名、意图混淆矩阵、失败用例归因分析（表达覆盖不足/槽位提取失败/路由错误/知识未命中等）、优化建议
- **FR-015** [UI:dialog-profile]: 系统必须支持版本发布功能：将对话方案（指令+知识库+人设）打包为统一版本发布，同一时间仅一个版本在生产环境生效
- **FR-016** [UI:dialog-profile]: 版本发布后，所有设备立即切换到新版本，现有设备会话上下文重置

**对话管理 API** *(FR-017 ~ FR-026，对应 US4-US6)*

- **FR-017** [API]: API 必须接收文本输入和设备上下文（设备ID、烹饪状态、炉门状态、当前温度、当前页面、屏幕信息等），返回统一格式的响应
- **FR-018** [API]: API 必须支持可配置的路由策略（默认指令优先），将用户输入分类到指令域/知识域/闲聊域
- **FR-019** [API]: 指令域必须返回结构化指令（意图标识+槽位参数）和确认回复文本；高风险操作（如高温加热超过 200℃、长时间烹饪超过 30 分钟）必须在回复中要求用户二次确认后才下发执行指令
- **FR-020** [API]: 当指令的必填槽位缺失或意图分类置信度低于阈值时，系统必须采用渐进式错误处理策略：第一次未识别 → 换种方式引导用户重新表达；第二次未识别 → 提供可能的选项列表供用户选择；第三次未识别 → 回复兜底话术并建议用户使用触屏操作。槽位追问提示优先使用 PM 配置的文案，若无配置则系统自动生成
- **FR-021** [API]: 知识域必须先在知识库中检索匹配，命中返回知识问答结果；未命中则降级到闲聊域
- **FR-022** [API]: 闲聊域必须基于 PM 配置的人设生成回复，支持联网内容查询（天气、股票、新闻等）
- **FR-023** [API]: API 必须维护会话上下文，按设备 ID 隔离，支持指代消解和省略恢复；会话超时时间可在对话方案中配置（默认 10 分钟无交互），超时后自动清除上下文
- **FR-024** [API]: API 必须自动检测输入语言（中文/英文），用对应语言回复；中英混杂时按中文优先
- **FR-025** [API]: 英文意图识别训练数据基于中文数据翻译生成
- **FR-026** [API]: API 统一响应格式必须兼容三种域类型（指令/知识/闲聊），包含：域类型、意图标识（指令域）、槽位列表（指令域）、回复文本、置信度、会话ID、是否需要追问、处理耗时

**监控与可观测性** *(FR-030 ~ FR-035，对应 US9)*

- **FR-030** [UI:monitoring]: 后台必须提供生产 API 的实时监控仪表盘，展示核心指标：总请求量、QPS、平均延迟、P95/P99 延迟、意图识别准确率（线上）、路由分布（指令/知识/闲聊占比）、错误率、平均对话轮次数。V2 追踪指标（需设备侧反馈）：对话完成率、用户满意度（重复率/放弃率/纠正率）、设备指令执行成功率
- **FR-031** [UI:monitoring]: 后台必须支持按设备 ID 查看该设备的所有历史会话列表（会话ID、起止时间、对话轮数、使用版本）
- **FR-032** [UI:monitoring]: 后台必须支持查看单个会话中每一轮请求的完整处理链路：输入文本、路由结果+置信度、意图分类+置信度、槽位提取详情、响应文本、处理耗时、设备上下文快照
- **FR-033** [API]: 每次 API 请求必须记录结构化日志，包含：请求ID、设备ID、会话ID、文本输入、路由结果、意图分类结果（含置信度）、槽位提取结果、最终响应、延迟、时间戳
- **FR-034** [UI:monitoring]: 后台请求日志必须支持多维筛选：时间范围、设备 ID、路由类型、意图名称、响应耗时区间、是否异常
- **FR-035** [UI:monitoring]: 系统必须支持告警规则配置，当意图识别准确率下降 > 5%、延迟 P99 超标、错误率突增时自动告警

**技术能力** *(FR-027 ~ FR-029，对应 US7)*

- **FR-027** [API]: 系统必须支持小模型+大模型结合的方案，小模型用于指令识别（需能在 Jetson Nano 上以 C++ 运行），大模型用于闲聊和知识问答
- **FR-028** [API]: 小模型训练后在各对话方案间共用；每个对话方案可独立配置大模型
- **FR-029** [API]: 联网内容能力必须集成 Brave Search API，支持实时查询天气、股票、新闻等外部信息

**安全与隐私** *(FR-036 ~ FR-037，章程对齐)*

- **FR-036** [Infra]: 对话历史、知识库文档等敏感数据在持久化存储中必须采用 AES-256 加密；数据库连接必须使用 TLS
- **FR-037** [Infra]: 系统必须提供设备维度的数据导出（JSON 格式）和数据删除 API，支持 GDPR 合规的用户数据管理；删除操作需管理员二次确认

**可用性与指令库闭环** *(FR-038 ~ FR-054)*

- **FR-038** [UI:monitoring]: 监控仪表盘数据刷新频率为 30 秒自动轮询，PM 也可手动刷新
- **FR-039** [UI:intent-library]: 系统必须支持指令库管理，指令库语种固定为中文/英文两类；`library_key` 全局唯一且创建后不可修改（如需变更必须删除重建）
  > 交互提示: 列表页 Table 展示所有指令库，新建弹窗中 Key 字段创建后不可修改
- **FR-040** [UI:dialog-profile]: 对话方案必须支持并行配置多个指令库，并提供“指令阈值”配置项；发布前必须校验方案配置合法性（包含指令库绑定与阈值范围）
- **FR-041** [API]: 运行时必须基于自动语言检测在对应语种指令库内匹配；英文输入未命中时不得回退中文指令库，必须进入知识域/闲聊域
- **FR-042** [Infra]: 存量迁移必须支持“现有意图默认迁入中文指令库、英文指令库后续补齐”的过渡策略
- **FR-043** [UI:intent-library]: 每个指令库必须支持多个小模型版本管理，单库模型数量上限为 5（代码常量）；超过上限时禁止新建训练任务并提示“请先归档/删除历史模型”
  > 交互提示: 详情页模型列表上方 Alert 展示当前数量/上限，超限时新建训练按钮禁用 + Tooltip
- **FR-044** [UI:intent-library]: 小模型版本状态机必须支持 `draft -> training -> trained -> evaluating -> testable -> published`，并支持归档后恢复为 `draft`
  > 交互提示: 详情页说明抽屉展示 G6 状态机图 + 横向 Tag 条
- **FR-045** [UI:intent-library]: 每个指令库同一时刻最多 1 个 `testable` 与 1 个 `published`；切换 `testable` 时必须自动取消旧 `testable`
- **FR-046** [UI:intent-library]: 系统必须允许同一模型同时持有 `testable` 与 `published` 状态
- **FR-047** [UI:dialog-profile]: 对话方案不强制绑定指令库；但若绑定某库，发布方案前必须校验该库存在 `published` 模型，否则禁止发布并给出明确提示
- **FR-048** [UI:intent-library]: 训练集与模型必须 1:1 关联；评估集与模型不要求 1:1；系统必须同时支持训练数据与评估数据两类 LLM 合成流程
  > 交互提示: 数据集页面用 Tag 标注绑定状态，1:1 训练集已绑定的删除按钮禁用
- **FR-049** [UI:intent-library]: 训练集导入最小字段固定为 `intent_key, utterance, language, slots(json), source(manual/llm)`；评估集导入采用全字段口径：`intent_key, utterance, language, source, expected_result, actual_result, threshold, actual_score, is_hit`，且 `actual_result/actual_score/is_hit` 允许为空并在评估后回填
- **FR-050** [UI:intent-library]: 质量阈值必须支持“库级默认 + 批量测试任务级单次覆盖并写快照”；`slot_f1` 仅在有槽位样本上计算；阈值用于结果展示和命中判断，不作为硬阻断
- **FR-051** [UI:intent-library]: 测试入口必须固定在“指令库 -> 模型 -> 测试”页面，提供对话框式单条测试（可展开详细结果）与批量测试两种模式
  > 交互提示: 测试页用 Tab 切换单条测试和批量测试
- **FR-052** [UI:intent-library]: 批量评估完成后必须自动生成智能分析，至少包含：总体结论、混淆意图 TopN（默认 5）、槽位错误类型分布、低分样本清单、改进建议
- **FR-053** [UI:intent-library]: 模型发布权限必须由 `model_publish` 控制，`testable` 管理权限必须由 `model_test_manage` 控制，权限校验以能力点为准不绑定角色名
- **FR-054** [UI:intent-library]: 小模型训练产物必须支持平台无关下载与运行：平台需提供模型下载能力（含版本元数据），并保证同一发布模型可在 Python 服务端与 C++ 设备端推理环境加载运行
  > 交互提示: 详情页模型版本操作列增加下载模型按钮

### 关键实体

- **DialogProfile（对话方案）**: 一套完整的对话管理配置，包含指令库引用（可多选并行）、指令阈值、知识库引用、闲聊人设、大模型选型、路由策略、会话超时时间（默认 10 分钟）；可创建多个方案，发布时选择一个生效
- **CommandLibrary（指令库）**: 指令集合容器，固定语种为中文或英文，包含 `library_key`（全局唯一且不可修改）、名称、描述、语种、关联意图数量
- **LibraryModelVersion（库模型版本）**: 指令库下的小模型版本实体，包含状态（draft/training/trained/evaluating/testable/published/archived）、训练集引用、评估记录、是否 testable/published 标记、模型产物下载地址与格式元数据（ONNX/TensorRT 等）
- **Intent（意图定义）**: 一个语义指令的完整描述，包含意图标识、中文描述、槽位定义、追问提示、训练数据/提示词；参考现有 39 个功能定义
- **Slot（槽位定义）**: 意图的参数定义，包含名称、实体类型、是否必填、追问提示、值约束
- **TrainingDataset（训练数据集）**: 模型训练样本集合，来源支持人工标注与 LLM 合成，最小字段为 `intent_key, utterance, language, slots, source`
- **EvaluationDataset（评估数据集）**: 模型评估样本集合，支持人工标注与 LLM 合成，导入支持全字段并允许结果类字段后回填
- **EvaluationRun（评估任务）**: 针对模型与评估集执行的一次批量评估，记录阈值快照、指标结果、命中率与智能分析产出
- **KnowledgeBase（知识库）**: 文档集合，按分类组织；每个文档经过解析后建立检索索引
- **Persona（闲聊人设）**: 定义助手的名称、性格特征、语气风格，用于约束大模型的回复风格
- **PublishedVersion（发布版本）**: 对话方案的快照，包含发布时间、关联方案ID；同一时间仅一个版本生效
- **DeviceSession（设备会话）**: 按设备 ID 隔离的运行时会话状态，包含对话历史、活跃实体栈、当前域状态；版本更新时重置；会话超时时间可在对话方案中配置（默认 10 分钟无交互自动清除上下文）
- **TestSuite（测试集）**: 批量测试用例的集合，包含自动生成和手动微调的用例，关联测试结果和分析报告
- **RequestLog（请求日志）**: 每次 API 请求的完整处理记录，包含请求ID、设备ID、会话ID、输入文本、路由结果、意图/槽位、响应内容、耗时、设备上下文快照、时间戳
- **AlertRule（告警规则）**: 监控告警配置，包含指标名称、阈值、持续时间、通知方式

## 成功标准 *(必填)*

- **SC-002**: 指令类语义理解端到端响应延迟 < 200ms（P95）
- **SC-003**: 知识问答/闲聊类响应延迟 2-4s
- **SC-004**: 同一意图的 10 种以上不同自然语言表达方式，系统能正确归一化识别
- **SC-005**: 系统支持中英文双语会话，自动检测语言并用对应语言回复
- **SC-006**: API 支持 10 QPS 并发，按设备隔离会话无状态冲突
- **SC-007**: PM 从创建对话方案到完成手动测试并发布版本，整个流程可在 1 小时内完成（验证方式：tasks 阶段实现端到端验收测试用例，模拟 PM 全流程操作并检查耗时）
- **SC-008**: 批量测试的智能分析报告能准确识别 80% 以上的识别失败根因
- **SC-009**: 通过"配置 → 测试 → 分析 → 优化 → 再迭代"闭环，每轮迭代使准确率提升可度量
- **SC-010**: 小模型可在 Jetson Nano 设备上运行（1.5GB 内存内，C++ 推理）
- **SC-011**: PM 可在后台按设备 ID 查看该设备所有历史会话及每轮请求的完整处理链路，支持多维筛选定位问题
- **SC-012**: 监控仪表盘实时展示 API 核心指标（QPS、延迟、准确率、路由分布），告警规则可配置并自动触发
- **SC-013**: 敏感数据（对话历史、知识库文档）在存储层加密，数据导出/删除 API 通过集成测试验证
- **SC-014**: 对话方案绑定指令库时，只有该库存在 published 模型方可发布方案；无 published 模型场景可被明确拦截并提示
- **SC-015**: 指令库模型测试支持单条测试与批量评估双入口，评估完成自动生成智能分析，且可展示阈值“预期值 vs 实际值”
- **SC-016**: 任一 published 模型可在平台下载，并在 Python 推理环境与 C++ 推理环境完成一致性加载验证（同版本模型可运行）
