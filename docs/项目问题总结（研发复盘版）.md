# 项目问题总结（研发复盘版）

## 一、复盘结论

本项目开发过程中遇到的问题，并不是单点代码缺陷过多，而是研发链路长期没有形成“同一事实源 + 真实完成定义 + 真实链路验证 + 缺陷回灌”的工程闭环。

从结果上看，代码、文档、任务、测试都“有”，但四者之间没有稳定对齐，所以项目会持续出现一种典型现象：

**局部看似都合理，整体一串就出问题。**

## 二、研发阶段实际遇到的主要问题

### 1. 任务完成定义失真

这是最核心的问题。

#### 具体表现

- `tasks` 中已经勾选完成，但正文仍写着“未实现”“待确认”“仅 UI”“未闭环”。
- 页面和接口已经建出来，但真实业务链路没有跑通。
- 进度统计和实际能力成熟度脱节。

#### 技术后果

- 研发以为后续是在“优化”，实际上还在“补主链路”。
- 测试范围被错误缩小，因为很多项已被误判为“完成”。
- 后面每次回补都要先重新识别什么是真的完成、什么只是表象完成。

### 2. 文档链漂移

#### 具体表现

- PD、AD、DD、plan、tasks 对同一个模块的边界、路径、页面、接口、FR 约束不一致。
- 历史上出现过：
  - `FR-047` 口径冲突
  - 页面数量和页面名不一致
  - 仓库路径引用错误
  - 接口路径层级不一致

#### 技术后果

- 开发可能严格实现了“错误版本的设计”。
- 测试和开发按不同文档验证，导致讨论时双方都觉得自己没错。
- 返工并不只是“改代码”，还需要先找准哪一版文档才算事实基线。

### 3. 假成功、假闭环、假进度

这是项目中最伤信任的一类问题。

#### 具体表现

- 前端给成功提示，但后端没有真实落地。
- UI 显示“生成成功”“执行成功”“分析完成”，但真实数据并不存在。
- 某些异步任务只是提交了请求，前端就展示为完成。
- 异常被吞掉后，页面看到的是空数据或默认值，而不是失败。

#### 技术后果

- 用户无法判断真实状态。
- 开发排障时很难分清是逻辑未执行、执行失败、还是结果未展示。
- 缺陷发现时间被拖后，且一旦发现往往已影响多个链路。

### 4. 契约不稳，前后端消费方式不一致

#### 具体表现

- 字段名不一致，如 `text` / `content`
- 返回结构不一致，如数组 vs `{ items, total, page }`
- 分页参数限制不一致，如前端按 200，后端只允许 100
- 路由写法不一致，如嵌套路由和顶级路由口径冲突

#### 技术后果

- UI 容易采用“猜 shape”的兼容写法，进一步放大不确定性。
- 契约一旦变更，很容易静默破坏现有页面。
- 问题常常不是接口 500，而是页面看起来“没数据”“不对劲”“统计不准”。

### 5. 异步链路和状态机设计不足

#### 具体表现

- 提交、处理中、完成、失败四类状态没有完整收口。
- 有些异步任务提交成功后，缺少可靠的状态回传和失败显示。
- 后端异步实现中还暴露出 ORM/事务/序列化等真实问题，例如 `MissingGreenlet`、后台执行失败不可见。

#### 技术后果

- 前端状态和后端状态经常脱节。
- 失败路径比成功路径更容易失控。
- 异步相关 bug 难以复现、难以自动覆盖、难以快速定位。

### 6. 测试没有始终围绕真实业务链路

#### 具体表现

- 有单测、契约测，但不一定覆盖真实使用方式。
- 测试更偏“接口存在”或“函数行为正确”，不够贴近“用户从入口到结果页”的完整链路。
- 很多问题在真实 smoke、真实页面跳转、真实权限、真实模型、真实异步执行下才暴露。

#### 技术后果

- 测试通过不等于可用。
- 工程质量信号失真。
- 回归保护不够贴业务，容易出现“修完一个点，又在真实链路别处炸掉”。

### 7. PD 很细，但任务拆解太粗

#### 具体表现

- PD 有很多交互要求，但任务只写成“实现某页面”。
- 页面实现成了骨架，但筛选、列定义、空态、弹窗、按钮、反馈、禁用态、异常态等大量细节未落地。
- `PD_FEATURE_GAP_ROOT_CAUSE_ANALYSIS` 里已经明确出现 40+ UI/功能差距。

#### 技术后果

- 页面是否“完成”缺乏明确判断标准。
- 开发以为只是补交互细节，实际是在补功能定义。
- 验收时才发现“页面有了，但功能密度远低于交互稿”。

### 8. 缺陷回灌不够强

#### 具体表现

- 缺陷文档、`INDEX`、workflow 已经有了，但早期更多是记录，不是阻断。
- 同类问题反复出现：假成功、契约漂移、路径不一致、权限遗漏、异步失败。
- 缺少稳定的“缺陷模式 -> 模板/规则/命令/测试”的强制回灌。

#### 技术后果

- 团队在重复踩同一类坑。
- 缺陷知识不能自动沉淀为工程资产。
- 每次改进都依赖人工记忆，不可持续。

### 9. 真实环境因素没有足够前置

#### 具体表现

- 代理端口、后端实际运行端口不一致会影响验证结论。
- 权限种子与新链路能力不一致，会导致真实账号无法操作。
- 模型状态、artifact 文件、真实数据库状态等运行态因素常在最后才暴露。

#### 技术后果

- 本地测试绿了，真实页面仍可能失败。
- 很容易把环境问题误判成代码问题，或反过来。
- 验证成本显著升高。

## 三、从研发角度看，问题的根因排序

如果按影响程度排序，我认为大致是：

### 第一层根因：完成定义失真

这是所有问题的放大器。只要“未完成也能报完成”，后面的文档、实现、测试都会被污染。

### 第二层根因：文档事实源不统一

没有统一事实源，开发和测试就很难稳定对齐。

### 第三层根因：缺少围绕核心业务链路的强验证

即使局部文档和代码都像样，只要没有真实业务链路 smoke，整体仍然可能不可用。

### 第四层根因：缺陷没有及时回灌成规则

导致同类问题无法系统性减少。

## 四、这次复盘中已经验证过的现实

通过本轮修整，可以明确看到：

- 一旦把文档基线对齐，很多实现问题会立即显性化。
- 一旦把“假成功”拿掉，真实缺陷会更快暴露，但工程状态反而更可信。
- 一旦围绕真实链路做 smoke，之前测试没发现的问题会被非常快地抓出来。
- 一旦把缺陷回灌到规则、模板、命令和任务结构里，治理会开始产生复利。

这说明项目并不是不能救，而是过去缺少强门禁，导致问题长期被延迟暴露。

## 五、研发层面的改进建议

### 1. 以后默认先问“证据是什么”，不要先问“做没做”

每个任务的完成，都需要至少绑定：

- 契约证据
- 真实链路证据
- 失败路径证据
- smoke 或 review 证据

### 2. 进入 `tasks` 前必须先做文档冲突扫描

如果 PD / AD / DD / plan 本身冲突，后续编码很大概率是在错误基线上推进。

### 3. 默认把“假成功”按严重失败处理

不要为了“用户体验友好”而隐藏真实失败。

### 4. 每个模块至少有 1-3 条核心业务链路回归

测试不再只按接口或页面拆，而是按用户真实目标拆。

### 5. 缺陷必须反向映射到规则、模板和命令

否则 defects 只是在存档，不是在减少未来缺陷。

## 六、最终研发判断

当前项目最大的经验教训是：

**研发过程不是缺文档，而是缺少把文档、任务、实现、验证拉到同一事实面上的强约束。**

过去的问题，本质上是“规范存在，但门禁不够硬；流程存在，但证据不够强；测试存在，但不够贴真实链路；缺陷存在，但没有充分回灌”。

如果这一轮建立起来的治理方式能继续坚持，后续模块的开发质量会明显提高；如果回到原来那种“先做再看、最后验收发现问题”的方式，那么同类问题会继续重复出现。
