# PD 功能缺失根因分析报告

> 生成日期：2026-03-20  
> 涉及缺陷：D031、D032、D033、D034、D035、D036  
> 涉及模块：指令库、知识库、对话方案、手动测试、批量测试、监控、用户管理  

---

## 一、问题概述

浏览器冒烟测试（`/speckit.smoke`）中发现 **6 个模块共 40+ 项前端功能** 与 PD（产品设计交互稿）存在显著差距，包括：统计卡缺失或命名不一致、表格列缺失、筛选器缺失、操作按钮缺失、整页 Placeholder 未实现等。

所有缺失功能在 PD HTML 交互稿中均有明确定义。

---

## 二、根因分析

通过对 PD → AD → DD → plan → tasks → implement 全链路的逐环审计，识别出以下 **5 个根因**：

### 根因 1：AD/DD 系统性忽略前端 UI 规格（核心原因）

| 维度 | AD/DD 覆盖情况 | 说明 |
|------|---------------|------|
| 后端 API 路由 | ✅ 覆盖率 ~90% | 几乎所有缺失功能的后端 API 已在 AD/DD 中设计 |
| 数据模型/Schema | ✅ 覆盖率 ~85% | 字段定义、枚举值、状态机基本完整 |
| **前端统计卡** | ❌ 覆盖率 ~0% | 无任何模块在 AD/DD 中定义统计卡的标签、数据来源 |
| **前端筛选器** | ❌ 覆盖率 ~20% | 仅 AD 中部分接口的 query 参数间接暗示了筛选维度 |
| **前端表格列** | ❌ 覆盖率 ~30% | AD 响应体字段列表存在，但未映射为前端表格列规格 |
| **前端交互组件** | ❌ 覆盖率 ~0% | Switch vs Button、弹窗倒计时、Timeline 等 UI 组件类型未定义 |

**结论**：AD/DD 文档采用了「API-first」的写作范式，聚焦后端接口契约和数据模型，**从未建立 PD 前端 UI 元素到 AD/DD 的映射规范**。这导致实现者在编写前端代码时缺乏设计依据，只能基于个人理解选择性实现。

### 根因 2：Tasks 粒度不足，未逐项枚举 PD UI 元素

| 任务文件 | 任务数 | 示例任务 | 问题 |
|---------|--------|---------|------|
| tasks-intent-library.md | 41 | T032: "搜索+筛选+Table+统计卡片" | 一个任务涵盖整个页面，未列出 PD 中的具体统计卡标签、筛选维度、表格列 |
| tasks-dialog-profile.md | 38 | T048: "列表+状态筛选+创建弹窗" | 同上 |
| tasks-monitoring.md | 27 | T062: "仪表盘+指标卡+趋势图" | 未明确 PD 要求的 8 个指标卡名称 |

**结论**：任务分解时以「页面级」为粒度，未将 PD 中的每个 UI 元素（按钮、列、筛选器、统计卡）拆解为可验收的 checklist 项。

### 根因 3：Plan/Tasks 目标项目不一致

- `plan.md` 和 tasks 文件中的路径引用指向 `smartchef-platform/`
- 实际实现在 `smartchef-v2/`
- 虽然功能范围一致，但项目切换时未重新校验 PD 覆盖率

### 根因 4：实现阶段缺少 PD 比对检查点

`/speckit.implement` 命令的模块检查点（Module Checkpoint）中：
- ✅ 有枚举一致性校验（DD 枚举 vs 代码）
- ✅ 有全局完成门禁（浏览器冒烟验证）
- ❌ **无 PD UI 覆盖率校验**——没有要求实现者在完成每个模块后逐项比对 PD 交互稿

### 根因 5：Placeholder 页面未纳入完成标准

`/intent-library/:id/test`、`/datasets`、`/datasets/:id` 三个路由在前端路由表中注册了 Placeholder 组件，但：
- 未在 tasks 中标记为「待实现」
- 未在模块检查点中标记为「未完成」
- Placeholder 的存在给人以「该路由已处理」的错觉

| 根因 | 影响缺陷数 | 影响 UI 元素数 | 严重程度 |
|------|-----------|--------------|---------|

## 四、改进建议

### 建议 1：DD 增加「前端 UI 组件清单」章节

在每个模块的 DD 文档中新增 `§前端 UI 组件清单` 节，格式如下：

```markdown
### §X.Y 前端 UI 组件清单

| PD 元素 | 组件类型 | 数据来源 (API/字段) | 备注 |
|---------|---------|-------------------|------|
| 指令库总数统计卡 | Card + Statistic | GET /intent-libraries → total | |
| 状态筛选器 | Select | query.status (draft/published) | |
| 模型版本 F1-Score 列 | Table Column | models[].metrics.f1 | |
| 启用/禁用切换 | Switch | PUT /users/{id} status | PD 明确要求 Switch |
```

### 建议 2：Tasks 拆解时增加 PD UI 逐项 Checklist

在 `/speckit.tasks` 命令中增加规则：
- 每个页面级任务 MUST 附带 PD UI Checklist
- Checklist 列出 PD 中该页面的：统计卡名称、表格列、筛选维度、操作按钮
- 每项对应一个可验收标准

### 建议 3：`/speckit.implement` 模块检查点增加 PD 覆盖率校验

在模块检查点（Module Checkpoint）中新增：

```
3. PD 覆盖率校验
   - 打开对应的 PD HTML 交互稿
   - 逐项比对统计卡、表格列、筛选器、操作按钮
   - 差异项必须标注为「有意省略」（附理由）或「待实现」
   - 覆盖率 < 80% 为 MAJOR 阻塞
```

### 建议 4：禁止 Placeholder 通过模块检查点

在 `/speckit.implement` 中增加规则：
- 路由表中注册的组件如果渲染为 `Result`/`Empty`/「Coming soon」等占位内容，**不得通过模块检查点**
- 必须要么实现完整功能，要么从路由表中移除并在 tasks 中标记为 P2/P3 延期

### 建议 5：`/speckit.smoke` 增加 PD 覆盖率维度权重

当前 speckit.smoke 的检查 8（PD 功能符合性）已存在，但建议提升其优先级：
- 将 PD 符合性检查从「补充维度」提升为「必检维度」
- 发现 PD 差距时自动生成缺陷文件（不再需要人工触发）

---

## 五、结论

PD 功能缺失的**核心根因是设计文档规范问题（根因 1）**，而非 PD 本身的问题。PD 内容完整且清晰，但 AD/DD 采用了纯后端视角的写作范式，系统性地忽略了前端 UI 规格的文档化。这一缺口在 tasks 分解（根因 2）和实现阶段的检查点（根因 4）中均未被捕获，最终导致 6 个模块共 40+ 项前端功能缺失。

**这不是执行力问题，而是流程规范问题。** 通过上述 5 项改进措施，可以从制度层面防止同类问题再次发生。
