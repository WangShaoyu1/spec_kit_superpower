# 项目问题总结（文档归档版）

## 一、背景

本总结基于以下三类材料综合整理：

- 规范修改文档
- 缺陷与审计文档
- 历次聊天过程中的问题发现、修复和验证记录

目标不是罗列单个 bug，而是总结当前项目开发过程中暴露出的系统性问题，为后续规范固化、模块扩展、缺陷治理和项目复盘提供统一材料。

## 二、总体判断

当前项目开发中遇到的主要问题，不是“文档太少”或“代码写错几个点”，而是研发闭环中的多个层面长期没有形成强一致：

- 文档层缺少统一事实源
- 任务层缺少真实完成定义
- 实现层存在契约漂移和异步失败路径缺口
- 验证层缺少围绕核心业务链路的强约束
- 缺陷层缺少稳定的反向回灌机制

最终导致的现象是：

**项目在局部看起来已经具备规范、页面、接口、测试，但一进入真实验收和真实串链，便出现大量“看似完成、实际未闭环”的问题。**

## 三、问题分类总结

### 3.1 完成定义失真

#### 现象

- `tasks` 中存在“已完成”与“未实现 / 待确认 / 未闭环”并存的情况。
- 完成率、页面完成状态、模块进度与真实可交付度不一致。
- 占位实现、演示流程、部分实现容易被误认为正式完成。

#### 根因

- DoD 更偏“做了哪些动作”，而非“拿什么证明已真实完成”。
- 缺少“无证据不得完成”的硬门禁。
- 缺少显式未完成声明机制，或机制虽有但未强执行。

#### 影响

- 项目进度被高估。
- 验收阶段返工集中爆发。
- 团队对模块成熟度认知不一致。

### 3.2 文档链漂移

#### 现象

- PD、AD、DD、plan、tasks 对同一能力边界和实现范围不一致。
- 需求条目、页面数量、路由路径、接口路径、仓库路径曾出现多处冲突。
- 同一 FR 在不同文档中的约束口径不统一。

#### 根因

- 文档多层维护，但缺少进入实施前的强制一致性扫描。
- 下游文档没有严格从上游派生，而是多份独立编辑。
- 设计变更后没有完整回拉整个文档链。

#### 影响

- 开发可能实现“错误版本的正确设计”。
- 测试与验收依据不一致。
- 返工需要同时处理文档和实现。

### 3.3 假成功、假进度、假闭环

#### 现象

- 前端给出成功提示，但后端未真实落地。
- 页面显示进度或结果，但实际状态并未完成。
- 任务只是提交成功，UI 却表现为业务成功。
- 异常被吞掉，页面仅显示空态或默认值。

#### 根因

- 早期缺少“反假成功”强规则。
- 设计与实现中对失败路径表达不足。
- 为了“流程顺滑”而弱化真实失败信号。

#### 影响

- 用户对系统结果失去信任。
- 开发难以快速判断失败发生在哪一层。
- 问题发现被延迟，且常常在最后阶段集中暴露。

### 3.4 前后端消费契约漂移

#### 现象

- 字段命名不一致。
- 返回包络形态不一致。
- 分页参数和限制不一致。
- API 路径口径不一致。
- 前端曾出现“猜返回结构”的兼容写法。

#### 根因

- 契约测试没有充分贴近真实前端消费方式。
- 接口结构变化没有同步回拉 DD/AD/前端。
- 页面实现对后端返回形态容错过度。

#### 影响

- 页面表现为数据空白、统计不准、功能异常。
- 小改动可能静默破坏现有功能。
- 排障困难，因为很多问题不表现为显式报错。

### 3.5 异步链路与状态机不足

#### 现象

- 提交中、处理中、完成、失败状态没有完整闭环。
- 后台任务失败时，前端无法及时得到真实反馈。
- 异步实现中暴露出事务、序列化、ORM 使用等技术问题。

#### 根因

- 设计更强调静态结构，较少强调运行期状态演化。
- 测试未把异步状态机作为高风险对象系统覆盖。
- 前后端都倾向于假设“最终会成功”。

#### 影响

- UI 状态和后端状态可能脱节。
- 用户看到成功，但真实数据未完成。
- 异步问题难复现、难验证、难回归。

### 3.6 测试未持续围绕核心业务链路

#### 现象

- 单测、契约测存在，但未必覆盖真实页面链路和真实业务目标。
- 大量问题在真实 smoke、真实权限、真实数据、真实环境下才暴露。
- 测试对“成功链路”关注较多，对“失败路径”和“真实页面消费”关注不足。

#### 根因

- 测试设计更偏接口维度、函数维度，而非用户目标维度。
- 缺少每模块 1-3 条核心业务链路的固定要求。
- smoke 早期更像页面巡检，而不是业务闭环验证。

#### 影响

- 测试通过不能代表系统可用。
- 验收仍需承担主要发现问题职责。
- 项目质量信号失真。

### 3.7 PD 到实现的映射不足

#### 现象

- PD 有较细交互设计，但 `tasks` 经常只有页面级描述。
- 页面骨架存在，但具体交互、筛选、表格列、空态、按钮、反馈态、禁用态不完整。
- smoke 对照 PD 时出现较多“功能差距”。

#### 根因

- AD/DD 偏 API-first、结构-first。
- `tasks` 粒度过粗，未形成交互级清单。
- implement/review/smoke 早期没有将 PD 对照纳入强门禁。

#### 影响

- 页面“看起来做了”，但离交互稿仍有显著距离。
- 功能差距容易在最后才被集中识别。
- 返工范围往往比预想更大。

### 3.8 缺陷治理回灌不足

#### 现象

- 缺陷有记录、有索引、有流程，但早期回灌力度不足。
- 同类问题反复出现，如假成功、路径不一致、权限缺失、契约不稳。
- 缺陷常停留在“发现和修复”，没有稳定升级成“规则和模板变更”。

#### 根因

- 缺陷治理更多是流程设计，自动化和强门禁不足。
- “本应被谁拦住”这一维度早期未被系统化使用。
- 模板、规则、命令、脚本与 defects 的联动不够紧。

#### 影响

- 组织学习速度慢。
- 相同问题重复出现。
- 缺陷处理成本持续偏高。

### 3.9 真实环境与权限因素暴露过晚

#### 现象

- 本地代理端口、真实后端端口、数据库状态、模型产物文件、权限种子等运行态条件会影响结论。
- 新链路接通后，真实账号权限不足会直接阻断用户操作。
- 模型状态可见，不代表 artifact 一定存在。

#### 根因

- 过去更关注静态实现是否存在，较少把真实环境证据纳入完成定义。
- 权限、数据、运行时资源状态未被纳入日常回归必查项。

#### 影响

- 代码层通过，但真实页面仍可能失败。
- 容易把环境问题误判为代码问题，或相反。
- smoke 与定位成本增加。

## 四、问题的结构性根因

综合来看，当前项目的问题可以归结为以下几个结构性根因：

### 4.1 缺少“证据驱动完成”

项目以前更多依赖描述性完成，而不是验证性完成。

### 4.2 缺少“单一事实源”

文档之间没有形成稳定的上游-下游派生关系。

### 4.3 缺少“围绕真实链路的默认验证”

测试和 smoke 并未始终站在真实用户目标视角组织。

### 4.4 缺少“缺陷模式自动回灌”

缺陷知识未完全转化为规则、模板、命令和脚本。

## 五、当前已经确认的改进方向

本轮规范修改和模块修整已经确认以下方向有效：

- 在 `tasks` 前引入 pre-flight 一致性扫描
- 在任务链中加入显式未完成声明
- 将“假成功”定义为严重失败
- 要求每个模块必须以核心业务链路做 smoke
- 用缺陷模式反向更新规则、模板和命令
- 强化文档链和实现链的同步回拉

这些措施已经开始明显改善“问题太晚暴露”的状况。

## 六、结论

当前项目开发中遇到的问题，本质上不是“写错了几个功能”，而是研发体系在很长一段时间里允许“表面完成”替代“真实完成”。

项目中最需要持续警惕的，不只是具体 bug 数量，而是以下几类高风险信号：

- 文档链冲突
- 任务完成定义失真
- 假成功
- 契约漂移
- 异步状态未闭环
- 测试不贴核心业务链路
- 缺陷未回灌

只要这些信号继续被系统性压制，项目就会逐步从“看似规范但不可交付”转向“证据充分、状态可信、可稳定扩展”。
