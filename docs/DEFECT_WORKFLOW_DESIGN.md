# 缺陷管理闭环方案（细化版 v2）

**目标**：建立「提缺陷 → 理解缺陷 → 解决缺陷 → 确认缺陷」的闭环，支持规则扫描、联动追踪与版本管理。

**已确定**：单缺陷单文件、MD 模板录入、手动触发规则、手动确认闭环；缺陷位于 `specs/master/defects/`，作为项目规范的重要组成部分。

---

## 一、核心流程

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  提缺陷     │ ──► │  理解缺陷   │ ──► │  解决缺陷   │ ──► │  确认缺陷   │
│ 复制模板    │     │ (分析归类)  │     │ (编码修复)  │     │ (手动验证)  │
│ 重命名填写  │     │ status 流转 │     │ fix_ref填写 │     │ status 已确认│
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

## 二、文件组织

```
specs/master/
  spec.md
  plan.md
  tasks.md
  defects/              # 缺陷管理（项目规范重要组成部分）
    INDEX.md            # 状态表（扫描时自动生成，便于查看与系统读取）
    _template.md        # 缺陷模板（复制此文件作为新缺陷）
    images/             # 缺陷截图，命名 D001-1.png、D001-2.png
    D001.md
    D002.md
    ...
    README.md           # 使用说明
```

**新增缺陷操作**：
1. 复制 `_template.md`
2. 重命名为 `D00x.md`（x 为当前最大编号 +1）
3. 截图放入 `images/`，命名为 `D00x-N.png`
4. 按模板填写内容

## 三、格式决策：MD vs YAML

**决策：采用 Markdown + YAML frontmatter**

| 对比 | Markdown + frontmatter | 纯 YAML |
|------|------------------------|---------|
| 现象/期望/复现步骤 | 正文用 Markdown，易写长文本 | 多行字符串，可读性差 |
| 截图引用 | `![描述](images/D001-1.png)` 原生支持 | 需额外结构 |
| 元数据 | frontmatter 结构化，可扫描 | 天然结构化 |
| 工具兼容 | Jekyll/Hugo 等通用 | 需自定义解析 |

结论：**MD + YAML frontmatter** 兼顾结构化元数据与富文本（含截图），为缺陷文档首选格式。

## 四、缺陷状态定义

| 状态 | 含义 | 下一步动作 |
|------|------|------------|
| 新建 | 刚建立缺陷，尚未录入完整 | 补全现象、期望、复现步骤，改为「待理解」 |
| 待理解 | 已录入，尚未分析 | 补充根因、修复方案，改为「已理解」 |
| 已理解 | 已分析清楚，可排期 | 开始修复，改为「修复中」 |
| 修复中 | 正在编码 | 提交代码、填写 fix_ref，改为「修复完成」 |
| 修复完成 | 代码已提交 | 手动回归验证 |
| 待确认 | 等待验证 | 验证通过后改为「已确认」，未通过改为「重新打开」 |
| 重新打开 | 验证未通过，需重新修复 | 重新修复后改为「修复中」 |
| 已确认 | 闭环完成 | 归档 |
| 已关闭 | 无需修复 / 重复 / 已废弃 | - |

**主流转**：新建 → 待理解 → 已理解 → 修复中 → 修复完成 → 待确认 → 已确认  

**回退流转**：待确认（验证未通过）→ 重新打开 → 修复中 → …

## 五、单条缺陷模板

见 `specs/master/defects/_template.md`。

**frontmatter 字段**（供规则扫描）：

| 字段 | 必填 | 说明 |
|------|------|------|
| id | 是 | 与文件名一致，如 D001 |
| status | 是 | 状态枚举值 |
| category | 是 | 接口 / UI / 业务 / 规范 / 需求 |
| severity | 否 | 高 / 中 / 低 |
| priority | 否 | P1 / P2 / P3 |
| created | 是 | 录入日期 YYYY-MM-DD |
| reporter | 否 | 录入人 |
| fix_ref | 否 | 修复后填写，commit / PR / 分支 |
| related | 否 | 扫描时自动分析填充，可手动覆盖 |

**正文区块**：现象（可含截图）、期望、复现步骤、根因、修复方案、修复说明。

**截图**：放入 `defects/images/`，命名 `D00x-N.png`，正文引用 `![描述](images/D001-1.png)`。

## 六、联动机制：自动分析缺陷与 spec / task / plan

### 6.1 自动分析（无需手动填写 related）

扫描脚本通过**分析缺陷正文**（标题、现象、期望、复现步骤等）自动匹配 spec/task/plan：

1. **直接提及**：正文中出现 `US1`、`T026` 等，直接加入关联
2. **用户故事关键词**：根据预置关键词（如 US1→指令配置/意图/槽位，US2→知识库/菜谱，US4→手动测试/调试面板 等）匹配
3. **任务关键词**：从 tasks.md 解析各任务描述，提取关键词，与缺陷正文匹配

### 6.2 执行方式

```bash
# 仅分析并输出，不写入文件
python scripts/scan_defects.py

# 自动将分析结果写入缺陷的 related 字段
python scripts/scan_defects.py --auto
```

`related` 格式：`US1, T026, T035`（逗号分隔，US 优先、T 其次）

### 6.3 规范文档版本（支持追溯）

在 spec.md、plan.md、tasks.md 顶部增加 YAML frontmatter，用于版本管理：

```yaml
---
version: 1.2
updated: 2026-03-10
changelog: |
  1.2: 根据 D001 修复调整 US1 验收场景
  1.1: 新增 US10 角色权限
---
```

- **version**：文档版本号，重大变更时递增
- **updated**：最后更新日期
- **changelog**：可选，记录与缺陷/版本相关的变更说明
- **Git 历史**：作为权威版本记录，frontmatter 便于快速查阅

### 6.4 手动覆盖

若自动分析不准确，可手动编辑缺陷的 `related` 字段，下次扫描 `--auto` 时会覆盖。建议在理解阶段复核自动关联结果。

## 七、规则扫描与自动化

**手动执行**：`python scripts/scan_defects.py`

**自动化**：Git pre-commit 钩子会在提交时检测 `specs/master/defects/` 的变更；若有缺陷文件被暂存，自动运行扫描并更新 `INDEX.md`，并将其加入本次提交。无需手动执行。

| 规则 | 输出 |
|------|------|
| R1 状态检查 | 状态不在枚举内的缺陷 |
| R2 必填检查 | 缺少 id/status/created/category 的缺陷 |
| R3 待理解超时 | 新建/待理解 超过 N 天未流转（可选） |
| R4 修复完成待确认 | 有 fix_ref 但 status 仍为「修复中」 |
| R5 待确认清单 | status=待确认 的缺陷列表 |
| R5b 重新打开清单 | status=重新打开 的缺陷列表 |
| R6 分类统计 | 各 category、status、priority 数量 |
| R7 联动 | 缺陷关联的 spec/task/plan 列表 |

## 九、变更规范文档时的建议流程

1. 修改 spec/plan/tasks 前，先确认是否有相关缺陷（扫描 R7 或搜索 `related`）
2. 修改后更新 frontmatter：`version`、`updated`、必要时补充 `changelog`
3. 若修改源于缺陷修复，在缺陷的「修复说明」中注明对应文档变更
