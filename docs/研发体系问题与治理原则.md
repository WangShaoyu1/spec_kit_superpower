# 研发体系问题与治理原则

## 一、目的

本文档用于保留本轮规范整理后仍然有效的核心结论：

- 当前研发体系曾暴露过哪些系统性问题
- 这些问题为什么会反复出现
- 后续规范收敛时应长期坚持哪些治理原则

本文档**不是历史案例汇编**，也**不是旧项目复盘归档**。它只保留对当前规范仍然有持续价值的内容。

## 二、核心问题

### 1. 完成定义失真

过去长期存在“任务显示完成，但能力并未真实闭环”的问题，具体表现为：

- 占位实现、部分实现、UI-only 实现被误算为完成
- 完成率、模块状态与真实可交付度不一致
- 验收阶段才集中发现主链路未完成

### 2. 文档链不一致

过去曾出现多个阶段文档对同一能力给出不同口径，导致：

- 设计真相不唯一
- 开发与测试依据不同版本工作
- 返工不仅是改代码，还要先修正事实基线

### 3. 假成功

过去反复出现“前端提示成功，但后端并未真实完成”的问题，包括：

- 假成功提示
- 假进度
- 假统计
- 假闭环

这类问题会直接破坏研发体系的可信度。

### 4. 测试与真实业务链路脱节

测试曾经更多覆盖局部接口或局部逻辑，而没有持续围绕“真实业务闭环”组织，导致：

- 单测和契约测通过，但真实链路失败
- 问题在人工验收时才被发现
- 回归保护不能真正代表可用性

### 5. 缺陷没有稳定回灌

缺陷被发现和修复过，但一段时间里没有稳定反向沉淀为：

- 规则
- 模板
- 命令
- 门禁

结果是同类问题反复出现。

## 三、当前体系应坚持的治理原则

### 1. 单一事实源

流程真相只允许有一套主入口：

- `.cursor/commands/README.md`
- `.cursor/rules/specify-rules.mdc`
- `.specify/templates/**`
- `.specify/scripts/**`

`docs/` 不再承担第二套流程定义职责。

### 2. 证据驱动完成

任务、模块、阶段是否完成，必须由证据决定，而不是由描述决定。

没有验证证据，不得宣称完成。

### 3. 反假成功

以下情况一律按失败处理：

- 未真实调用后端却提示成功
- 异步任务只提交成功却显示业务成功
- 结果、进度、统计来自硬编码或猜测
- 占位能力被当作正式能力

### 4. 核心链路优先

每个模块都必须围绕真实闭环定义核心业务链路，并在：

- plan
- tasks
- implement
- review
- smoke

中持续引用和验证。

### 5. 缺陷必须反向改规范

修缺陷不能只停留在业务代码层。

每次处理缺陷时，都应判断：

- 这个问题本应被哪个阶段拦住
- 是否需要回改规则、模板、命令或脚本

## 四、当前定位

当前规范体系已经不再是原始的轻流程框架，但也还没有完全达到“生成级研发体系”的最终形态。

它目前更接近：

**以设计链和门禁链为核心的研发流程骨架**

后续继续优化时，应优先做：

1. 统一流程真相
2. 收紧硬门禁
3. 压缩规范冗余
4. 稳定缺陷回灌

而不是继续扩张文档体积。

## 五、使用边界

本文档只保留长期有效的治理原则。

如果未来再次形成大规模审计、复盘或专项根因分析，应优先沉淀到核心规范中；仅当内容确实需要长期保留时，才应以新文档形式进入 `docs/`。
