# 研发体系问题与治理原则

## 一、目的

本文档用于保留本轮规范整理后仍然有效的核心结论：

- 当前研发体系曾暴露过哪些系统性问题
- 这些问题为什么会反复出现
- 后续规范收敛时应长期坚持哪些治理原则

本文档**不是历史案例汇编**，也**不是旧项目复盘归档**。它只保留对当前规范仍然有持续价值的内容。

## 二、核心问题

### 1. 完成定义失真

过去长期存在“任务显示完成，但能力并未真实闭环”的问题，具体表现为：

- 占位实现、部分实现、UI-only 实现被误算为完成
- 完成率、模块状态与真实可交付度不一致
- 验收阶段才集中发现主链路未完成

### 2. 文档链不一致

过去曾出现多个阶段文档对同一能力给出不同口径，导致：

- 设计真相不唯一
- 开发与测试依据不同版本工作
- 返工不仅是改代码，还要先修正事实基线

### 3. 假成功

过去反复出现“前端提示成功，但后端并未真实完成”的问题，包括：

- 假成功提示
- 假进度
- 假统计
- 假闭环

这类问题会直接破坏研发体系的可信度。

### 4. 测试与真实业务链路脱节

测试曾经更多覆盖局部接口或局部逻辑，而没有持续围绕“真实业务闭环”组织，导致：

- 单测和契约测通过，但真实链路失败
- 问题在人工验收时才被发现
- 回归保护不能真正代表可用性

### 5. 缺陷没有稳定回灌

缺陷被发现和修复过，但一段时间里没有稳定反向沉淀为：

- 规则
- 模板
- 命令
- 门禁

结果是同类问题反复出现。

### 6. PD 对 AI 不可操作

过去默认认为“PD 写清楚了，AI 自然能实现出来”，但实践表明这并不成立。

问题不只在于 AI 是否读了 PD，更在于 PD 是否以 AI 可执行的方式表达：

- 大量真正影响实现的产品语义被放在 Drawer / Modal / 说明区域中
- 页面主骨架与隐藏交互之间缺少结构化区分
- 规则层一度把 `说明按钮 / Drawer` 当作“不纳入 PD 检查”的内容
- 结果是 AI 更容易只实现主页面骨架，而忽略 Drawer 内承载的产品功能

这会导致一种新型失真：

- 人看 PD 时觉得“写得很清楚”
- AI 做实现时却只提取到页面边界和表层入口
- 流程检查又没有把隐藏交互当作必须承接的功能
- 最终在人工验收时才发现“说明里写了，但系统没做”

## 三、当前体系应坚持的治理原则

### 1. 单一事实源

流程真相只允许有一套主入口：

- `.cursor/commands/README.md`
- `.cursor/rules/specify-rules.mdc`
- `.specify/templates/**`
- `.specify/scripts/**`

`docs/` 不再承担第二套流程定义职责。

### 2. 证据驱动完成

任务、模块、阶段是否完成，必须由证据决定，而不是由描述决定。

没有验证证据，不得宣称完成。

### 3. 反假成功

以下情况一律按失败处理：

- 未真实调用后端却提示成功
- 异步任务只提交成功却显示业务成功
- 结果、进度、统计来自硬编码或猜测
- 占位能力被当作正式能力

### 4. 核心链路优先

每个模块都必须围绕真实闭环定义核心业务链路，并在：

- plan
- tasks
- implement
- review
- smoke

中持续引用和验证。

### 5. 缺陷必须反向改规范

修缺陷不能只停留在业务代码层。

每次处理缺陷时，都应判断：

- 这个问题本应被哪个阶段拦住
- 是否需要回改规则、模板、命令或脚本

### 6. PD 必须同时服务人和 AI

PD 不能只追求“人能看懂”，还必须追求“AI 能执行、门禁能检查”。

后续应默认采用双层表达：

- 视觉层：HTML 原型、页面边界、导航路径、交互大致布局
- 语义层：结构化页面能力清单，明确哪些是主页面元素，哪些是隐藏交互容器中的真实功能

其中语义层至少要显式列出：

- 页面可见元素（表格、筛选器、统计卡、主按钮）
- 隐藏交互容器（Drawer / Modal / Popover / 展开面板）
- 每个操作的前置条件、成功信号、失败反馈、状态变化
- 字段与数据契约
- 业务规则与 FR 映射

如果某项内容只是辅助说明而不是产品功能，也必须显式标注为解释性内容，而不能靠阅读者自行猜测。

### 7. 隐藏交互中的产品功能必须纳入覆盖率

视觉上不在首页主区域，不等于产品上不重要。

凡是满足以下条件的 Drawer / Modal / Popover / 二级面板，都必须视为产品功能的一部分：

- 用户可以在其中新增、编辑、删除、导入、导出、提交、切换状态
- 用户可以在其中配置业务规则、实体、词槽、阈值、映射关系
- 用户可以在其中触发影响真实状态的操作

这类内容后续必须同时进入：

- PD 页面能力清单
- DD 前端交互规格
- plan / tasks
- implement 检查点
- smoke / audit / harness

不能再按“说明区域”排除。

## 四、当前研发主链与 Harness 位置

### 1. 研发主链

```text
spec
  -> HumanPD (pd-all/)
  -> AI-PD (ai-pd/)
  -> AD
  -> DD
  -> plan
  -> tasks
  -> implement
  -> smoke
  -> review / 验收
```

### 2. Harness 的位置

`harness` 不是上述链条中的某一个单独阶段，而是贯穿 `AI-PD -> AD -> DD -> plan -> tasks -> implement -> smoke` 的执行控制层与门禁层。

可以把它理解成：

```text
研发产物流:
spec -> HumanPD -> AI-PD -> AD -> DD -> plan -> tasks -> implement -> smoke -> review

Harness 治理层:
          [前置检查 / gate / 模块状态 / 风险继承 / browser probes]
          └────────────────────────────────────────────────────────┘
```

它主要负责：

- 检查阶段输入是否齐全
- 检查上游风险是否被下游显式继承
- 控制模块推进顺序与状态流转
- 在 `tasks / implement / browser` 等阶段执行 gate
- 防止跳过文档链直接进入实现或验收

### 3. 质量把关落点

当前体系的质量把关不是只靠测试，而是分层完成：

- 文档链把关：`HumanPD -> AI-PD -> AD -> DD -> plan -> tasks` 必须顺序闭合
- Harness 把关：`check-prerequisites` + `validate-stage-gates` 拦截缺输入、缺引用、风险未继承
- 测试把关：契约测试、集成测试、页面测试、消费契约测试
- Browser / smoke 把关：验证 `page_boundary_parity`、`route_navigation_chain`、`capability_parity` 与真实结果回读
- Review / 验收把关：最终以真实业务闭环和缺陷回灌收口

## 五、当前定位

当前规范体系已经不再是原始的轻流程框架，但也还没有完全达到“生成级研发体系”的最终形态。

它目前更接近：

**以设计链和门禁链为核心的研发流程骨架**

后续继续优化时，应优先做：

1. 统一流程真相
2. 收紧硬门禁
3. 压缩规范冗余
4. 稳定缺陷回灌
5. 提升 PD 对 AI 的可操作性

而不是继续扩张文档体积。

## 六、使用边界

本文档只保留长期有效的治理原则。

如果未来再次形成大规模审计、复盘或专项根因分析，应优先沉淀到核心规范中；仅当内容确实需要长期保留时，才应以新文档形式进入 `docs/`。
