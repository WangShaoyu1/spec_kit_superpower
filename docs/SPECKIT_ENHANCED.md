# Spec-Kit 增强流程指南

## 背景：为什么需要增强流程？

### 原流程的问题
```
spec.md (业务需求) → plan.md → tasks.md → 代码
         ↑                              
         └── 缺失产品交互细节 ──────┐    
         └── 缺失架构设计 ─────────┼────→ 30% 逻辑偏差
         └── 缺失详细设计 ─────────┘
```

### 实际案例
- **D014**: 指令库语种化、方案阈值、编辑弹窗双列布局 → 都是 PD 层缺失
- **D016**: 小模型状态机、训练链路、权限点、数据集口径 → 都是 AD/DD 层缺失

### 增强后的流程
```
specify (需求澄清)
    ↓
spec.md ───────→ pd.md (产品交互设计)
    ↓                ↓
    └──────────────→ ad.md (架构设计)
                         ↓
                    dd.md (详细设计)
                         ↓
                    plan.md (实施计划)
                         ↓
                    tasks.md (任务清单)
                         ↓
                    implement (代码实现)
```

## 新流程的核心改进

| 阶段 | 新增文档 | 解决的问题 | 降低偏差 |
|-----|---------|-----------|---------|
| specify | spec.md | 业务需求澄清 | 15% |
| design-pd | pd.md | 页面状态、交互细节 | 35% |
| design-ad | ad.md | 模块关系、数据流、接口 | 25% |
| design-dd | dd.md | 字段定义、状态机、错误码 | 25% |
| plan | plan.md | 精确任务拆解 | - |
| implement | 代码 | 按设计精确实现 | - |

**总计**: 从 70% → 95%+ 准确率

## 快速开始

### 1. 初始化项目结构

```bash
# 创建功能分支目录
mkdir -p specs/{branch}/{defects,contracts}
cp specs/_template/*_template.md specs/{branch}/
```

### 2. 按顺序执行设计阶段

| 命令 | 输入 | 输出 | 检查点 |
|-----|------|------|--------|
| `/speckit.specify` | 业务背景 | spec.md | 验收场景完整 |
| `/speckit.design-pd` | spec.md | pd.md | 状态矩阵覆盖 |
| `/speckit.design-ad` | spec+pd | ad.md | 数据流完整 |
| `/speckit.design-dd` | spec+ad | dd.md | 字段级定义 |
| `/speckit.plan` | spec+pd+ad+dd | plan.md | 任务可执行 |
| `/speckit.tasks` | plan.md | tasks.md | 依赖清晰 |
| `/speckit.implement` | tasks.md | 代码 | 符合设计 |

### 3. 每个阶段必须完成的检查清单

#### specify → spec.md
- [ ] 所有用户故事都有 Given-When-Then 验收场景
- [ ] 关键术语已定义（实体/状态/角色）
- [ ] 边界情况已列出
- [ ] 成功标准可量化

#### design-pd → pd.md
- [ ] 每个用户故事映射到具体页面
- [ ] 关键页面有状态矩阵（正常+异常）
- [ ] 危险操作有二次确认定义
- [ ] 布局规则一致（简单项双列、复杂项整行）

#### design-ad → ad.md
- [ ] 模块职责清晰，无循环依赖
- [ ] 核心流程有数据流图
- [ ] 接口契约完整（路径、输入、输出、错误码）
- [ ] 性能目标可量化

#### design-dd → dd.md
- [ ] 数据模型有字段级定义（类型、约束、索引）
- [ ] 状态机转移有触发条件和校验
- [ ] 核心算法有伪代码和边界处理
- [ ] 错误码覆盖所有业务异常
- [ ] 权限点粒度合适

## 文档追溯关系

每个文档必须包含追溯矩阵：

```markdown
## 追溯矩阵

| 本文档章节 | 上游文档章节 | 说明 |
|-----------|-------------|------|
| PD-3.1 手动测试状态 | spec.md US4 | 页面状态映射 |
| DD-2.1 模型状态机 | spec.md FR-044 | 状态流转实现 |
```

## 实际案例：D016 按新流程重做

### 原流程（产生缺陷）
```
spec.md: "指令库管理" (笼统描述)
    → plan.md: 粗略技术方案
    → tasks.md: 只包含 CRUD 任务
    → 实现: 只有列表增删改查
    → ❌ 缺陷: 训练链路、状态机、权限点全部缺失
```

### 新流程（完整覆盖）
```
spec.md: "指令库管理"
    → pd.md: 
        - 指令库页面流程
        - 模型测试页交互（单条/批量）
        - 发布确认弹窗
    → ad.md:
        - 模块: 指令库/模型/训练/评估/方案
        - 数据流: 数据→训练→评估→发布→生效
        - 接口: 训练任务创建、评估执行、发布
    → dd.md:
        - 模型状态机: draft→training→trained→...
        - 数据字段: 训练集/评估集字段口径
        - 权限点: model_publish, model_test_manage
        - 配置: 阈值层级、模型上限
    → plan.md: 精确到每个子模块的任务
    → tasks.md: 覆盖全链路的任务清单
    → 实现: 完整的小模型闭环
```

## 现有项目如何迁移？

### 阶段 1: 补充当前迭代的 PD/AD/DD
- 当前正在进行的缺陷（D016 及以后）
- 使用新流程补充 pd.md / ad.md / dd.md
- 然后继续 plan → tasks → implement

### 阶段 2: 追溯补全历史设计
- 高优先级：D014、D016（影响架构的缺陷）
- 中优先级：其他已关闭缺陷
- 低优先级：已稳定的功能模块

### 阶段 3: 更新工具和模板
- ✅ 已完成：新增命令文件
- ✅ 已完成：新增模板文件
- 后续：更新 `.cursor/rules` 引用新流程

```markdown
- [ ] 每个关键实体都有字段级定义
```
