

# SmartChef NLU 项目章程

## 核心原则

### I. 意图优先架构

系统 MUST 以意图识别（Intent Recognition）为核心进行架构设计，  
严格分离意图分类、槽位填充（Slot Filling）和对话管理三个层次。  
本项目专注于语义理解能力，接收上游 ASR 模块输出的文本作为输入，  
不涉及语音信号处理和语音识别环节。

- 每个文本输入 MUST 经过统一的 NLU Pipeline 处理：
文本输入 → 文本预处理 → 意图分类 → 槽位提取 → 对话状态管理 → 响应生成
- 意图体系 MUST 采用层级化设计：顶层域（command / chitchat / preference）→ 子意图 → 具体动作
- 新增意图 MUST 通过注册机制接入，禁止硬编码分支判断
- 意图分类置信度低于阈值时 MUST 触发澄清对话（clarification），禁止静默回退
- 理由：意图优先确保系统可扩展、可测试，避免意大利面条式的条件分支，
是语义理解系统的行业标准架构模式（参考 Rasa、Dialogflow 设计哲学）

### II. 领域驱动设计

所有功能 MUST 按业务领域（Bounded Context）组织，每个领域自包含、可独立演进。

- 核心领域划分：
  - **指令域**（Command）：涵盖设备控制指令（开始/暂停/停止烹饪、温度调节、
  定时器等）和菜谱操作指令（菜谱搜索、推荐、收藏、步骤导航等）。
  菜谱管理类指令 MUST 与设备端菜谱 UI 界面联动，语义理解结果
  MUST 映射为 UI 界面可消费的结构化操作指令（如页面跳转、列表筛选、
  步骤切换等），确保语音交互与手动触屏操作体验一致
  - **闲聊域**（Chitchat）：日常对话、烹饪知识问答、情感交互
  - **用户偏好域**（User Preference，V2 规划）：操作习惯记忆、口味偏好、饮食限制、个性化推荐。V1 不含此域，作为 V2 扩展规划
- 领域间通信 MUST 通过定义良好的接口（事件/消息），禁止领域间直接依赖
- 每个领域 MUST 拥有独立的意图集、槽位定义和对话流程
- 领域模型变更 MUST 有明确的版本管理和向后兼容策略
- 理由：领域驱动设计确保系统模块化，各领域团队可并行开发，
新领域（如健康管理、购物清单）可通过插件方式无侵入接入

### III. 测试驱动开发（不可协商）

TDD 强制执行：编写测试 → 测试失败 → 实现代码 → 测试通过 → 重构。

- NLU 模型 MUST 有标准化的测试数据集（训练集/验证集/测试集严格分离）
- 意图分类 MUST 达到以下基线指标：
  - 指令类意图（设备控制 + 菜谱操作）：F1-Score ≥ 0.95
  - 闲聊类意图：F1-Score ≥ 0.85
  - 用户偏好类意图（V2 规划）：F1-Score ≥ 0.90
- 槽位提取 MUST 达到 Entity-level F1-Score ≥ 0.90
- 对话流程 MUST 有端到端（E2E）测试覆盖所有关键路径
- 回归测试 MUST 在每次模型/代码变更后自动执行
- 集成测试重点领域：NLU Pipeline 端到端、指令域语义解析与 UI 指令映射、
跨领域上下文切换、API 请求日志完整性（V2 追加：用户偏好持久化与召回）
- 理由：厨电设备误操作可能导致安全隐患，
TDD 是确保语义理解系统可靠性的最低要求

### IV. 数据管道完整性

训练数据、模型产物和推理管道 MUST 全链路版本化、可复现、可审计。

- 训练数据 MUST 使用版本控制（DVC 或等效工具），每次训练可追溯到精确数据快照
- 模型产物 MUST 包含元数据：训练数据版本、超参数、评估指标、训练时间戳
- 推理管道 MUST 支持灰度发布和快速回滚（A/B Testing、金丝雀发布）
- 数据标注 MUST 有质量控制流程：双人标注 + 仲裁机制，标注一致性（Cohen's Kappa）≥ 0.80
- 禁止在生产环境直接修改模型或数据；所有变更 MUST 经过完整的 CI/CD 管道
- 理由：ML 系统的可复现性是调试和持续改进的基础，
数据和模型的不可追溯是 ML 项目失败的首要原因（参考 Google MLOps 成熟度模型）

### V. 对话体验一致性

所有对话交互 MUST 遵循统一的对话设计规范（Conversation Design Guidelines）。

- 系统回复 MUST 保持一致的人设（Persona）：友好、专业、简洁
- 回复 MUST 遵循分层信息架构：核心确认 → 补充信息 → 引导下一步
- 错误处理 MUST 遵循渐进式策略：
第一次未识别 → 换种方式引导；
第二次未识别 → 提供选项列表；
第三次未识别 → 转人工或退出
- 多轮对话 MUST 维护上下文状态，支持指代消解和省略恢复
- 设备控制类回复 MUST 包含操作确认和状态反馈
- 所有用户可见文本 MUST 支持国际化（i18n），默认中文简体
- 理由：对话体验的一致性直接影响用户信任度和产品留存率，
不一致的回复风格会严重损害用户对语音助手的信心

### VI. 可观测性与指标驱动

每个推理请求、意图分类和对话轮次 MUST 有完整的监控和追踪。

- 核心业务指标 MUST 实时监控：
  - 意图识别准确率（线上）
  - 对话完成率（Task Completion Rate）
  - 用户满意度（通过隐式信号：重复率、放弃率、纠正率）
  - 平均对话轮次数（越少越好）
  - 设备指令执行成功率
- 每次推理 MUST 记录结构化日志：请求ID、用户ID、文本输入、
意图分类结果（含置信度）、槽位提取结果、最终响应、延迟
- 异常检测 MUST 自动告警：意图分类准确率下降 > 5%、延迟 P99 超标、错误率突增
- 理由：ML 系统的静默退化（silent degradation）是最危险的失败模式，
完善的可观测性是早期发现和快速响应问题的唯一保障

### VII. 安全与隐私优先

用户数据、偏好和对话历史 MUST 以加密存储和基于同意的访问控制为前提。

- 用户偏好和对话历史 MUST 加密存储（AES-256 或等效算法）
- 用户数据访问 MUST 基于最小权限原则，所有访问留审计日志
- 系统 MUST 支持用户数据导出和删除请求（GDPR/个人信息保护法合规）
- 设备控制指令 MUST 有安全校验：高风险操作（如高温加热）需要二次确认
- 禁止将用户个人数据用于模型训练，除非获得明确同意且数据经过脱敏处理
- 理由：智能家居产品涉及用户隐私和人身安全，
安全与隐私 MUST 作为架构级约束而非事后补丁。
语音/音频数据的安全由上游 ASR 模块负责，不在本项目范围内

## 技术约束与标准

- **响应延迟**: NLU 推理端到端延迟 MUST < 200ms（P95），
设备控制指令下发 MUST < 500ms（P95）
- **并发处理**: 系统 MUST 支持同一家庭内多设备并发交互，无状态冲突
- **离线能力**（V2 规划）: V1 不支持离线，因上游 ASR 模块为在线服务，
  断网后无文本输入。V2 可评估设备端小模型结合本地 ASR 的离线方案
- **设备兼容**: NLU 服务 MUST 与具体硬件型号解耦，
通过设备能力描述文件（Device Capability Profile）适配不同厨电设备
- **API 规范**: 所有服务间接口 MUST 遵循 RESTful 或 gRPC 规范，
提供 OpenAPI/Protobuf 定义文件
- **代码质量**: 代码 MUST 通过静态分析（linter）和格式化检查，
核心模块测试覆盖率 MUST ≥ 80%
- **依赖管理**: 所有第三方依赖 MUST 有明确版本锁定，
安全漏洞 MUST 在 72 小时内响应

## 开发工作流与质量门禁

- **分支策略**: 采用 Git Flow 或 Trunk-Based Development，
所有功能开发 MUST 在功能分支上进行
- **代码审查**: 所有合并到主分支的代码 MUST 通过至少一人的 Code Review
- **CI/CD 门禁**:
  - 单元测试通过率 100%
  - 集成测试通过率 100%
  - NLU 模型评估指标不低于基线（不允许退化）
  - 静态分析零严重/高危告警
  - 安全扫描通过
- **发布流程**: 模型和代码的发布 MUST 解耦，支持独立部署和回滚
- **文档要求**: 每个公开 API MUST 有 OpenAPI 文档，
每个领域模块 MUST 有 README 说明用途、接口和使用方法
- **变更管理**: 破坏性变更 MUST 遵循语义版本控制，
提前一个版本标记为 deprecated 并提供迁移指南

## 治理

- 本章程是项目的最高指导原则，优先于所有其他实践文档和约定
- 修正本章程 MUST 遵循以下流程：
  1. 提出修正提案并说明理由
  2. 评估对现有原则和下游制品的影响
  3. 获得项目负责人批准
  4. 更新章程并递增版本号
  5. 同步更新所有受影响的模板和文档
- 版本控制策略：
  - MAJOR：原则删除、重新定义或不兼容的治理变更
  - MINOR：新原则/部分添加或实质性扩展
  - PATCH：澄清、措辞优化、拼写修复
- 所有 PR/代码审查 MUST 验证与本章程的合规性
- 复杂性引入 MUST 有充分的证明理由，简单方案优先（YAGNI 原则）
