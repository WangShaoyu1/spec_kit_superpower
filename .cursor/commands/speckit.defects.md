## 用户输入

```text
$ARGUMENTS
```

在继续之前，你**必须**考虑用户输入（如果不为空）。
常见用法：
- `/speckit.defects` — 仅执行扫描与统计
- `/speckit.defects --auto` — 扫描并自动写入 related 字段
- `/speckit.defects 新增了缺陷 D0xx.md，请解决` — 扫描 + 修复指定缺陷
- `/speckit.defects D0xx D0yy` — 批量修复多个缺陷

## 目标

提供**缺陷全生命周期闭环管理**，覆盖：发现、分类、分析、修复、设计回溯、验证。
将原先分散的缺陷扫描流程与 `speckit.fixbug` 修复流程统一收口为 `/speckit.defects`。

## 核心原则

- **最小化修改**: 只修改与缺陷直接相关的代码，避免对其他功能造成影响
- **设计回溯**: 修复不仅要改代码，更要检查设计文档是否需要同步更新
- **闭环验证**: 修复完成后 MUST 运行测试 + 更新缺陷状态，禁止"修了就算"
- **分类路由**: 不同类型的缺陷走不同的处置路径（代码修复 / 设计补充 / 需求回溯）
- **治理回灌**: 每个缺陷都要回答"本应由哪个环节拦住", 反向更新规则/模板/命令

## 执行流程

### Phase 1: 缺陷扫描与发现

从仓库根目录执行：

```bash
python scripts/scan_defects.py
```

若用户指定 `--auto`，则执行：

```bash
python scripts/scan_defects.py --auto
```

`--auto` 会将 R7 联动分析结果自动写入各缺陷的 `related` 字段。

**Token 节省**：INDEX.md 为轻量入口，扫描后先读 INDEX.md 概览，再按需读取具体 D*.md，避免全量读取缺陷文件。

#### 扫描输出解读

| 规则 | 说明 |
|------|------|
| R1 状态检查 | 状态不在枚举内的缺陷需修正 |
| R2 必填检查 | 缺少 id/status/created/category 的缺陷需补全 |
| R4 修复完成 | 有 fix_ref 但 status 仍为「修复中」的，建议改为「修复完成」 |
| R5 待确认 | 需回归验证的缺陷 |
| R5b 重新打开 | 验证未通过、需重新修复的缺陷 |
| R6 统计 | 按分类、状态、优先级汇总 |
| R7 联动 | 自动分析出的 spec/task/plan 关联 |
| R8 分类路由 | 根据 category 推荐处置路径（代码修复/设计补充/需求回溯） |

**若用户仅要求扫描（无修复指令），到此结束。**
**若用户指定了待修复的缺陷，继续 Phase 2。**

---

### Phase 2: 缺陷分类与路由

读取指定缺陷文件（按需读取，不全量加载），根据缺陷 `category` 和根因判断处置路径：

| 缺陷类型 | 判断依据 | 处置路径 |
|----------|---------|---------|
| **代码 bug** | category=接口/UI，根因在实现层 | Phase 3→4→5→6（本命令内完成） |
| **设计遗漏** | category=业务/规范，根因在 AD/DD 层 | 回到 `/speckit.design-dd` 补设计 → 补 tasks → 实现 |
| **需求变更** | category=需求，需要改交互或新增功能 | 回到 `/speckit.specify` 或 `/speckit.design-pd` |

**路由决策规则**：
1. 读取缺陷的 `category`、`severity`、现象描述和根因（若已填写）
2. 如果根因明确指向代码实现层（如本次 D017 的 capability key 拼写错误）→ **代码修复**路径
3. 如果根因指向设计文档缺失或矛盾（如 DD 中未定义某状态转换）→ **设计补充**路径，告知用户需先补设计再修复
4. 如果本质是功能缺失或交互变更（如需要新增一个模态框）→ **需求回溯**路径，告知用户需先更新 spec/pd

**对于设计补充和需求回溯路径**：输出建议后**停止**，等待用户确认并执行对应的 design/specify 命令后，再回到本命令继续修复。

---

### Phase 3: 根因分析与定位（代码修复路径）

- **理解缺陷**: 明确症状、复现步骤和期望行为
- **定位相关文件**: 确定可能包含 bug 的文件和代码区域
- **分析错误日志**: 如果有错误日志，分析异常堆栈和错误信息
- **版本历史检查**: 查看最近的代码变更，识别可能引入 bug 的提交

**根因记录**: 将分析结论写入缺陷文件的「根因」章节。

---

### Phase 4: 修复实施

- **精确修改**: 针对已识别的问题进行最小化的代码修改
- **遵循代码风格**: 确保修复代码遵循项目现有的代码风格和规范
- **考虑边界情况**: 确保修复不会在边界情况下导致新的问题
- **同步编写测试**: 修复代码 MUST 同批次附带测试用例（至少覆盖修复点 + 回归路径）

---

### Phase 5: 设计文档回溯

> **来源**: 建议 1 — 防止设计-代码长期漂移

修复完成后，**MUST** 执行以下检查：

1. **设计一致性检查**: 修复是否暴露了 AD/DD 文档的不一致？
   - 检查 DD 中的**枚举定义**（权限点 key、错误码、状态枚举）与代码是否一致
   - 检查 AD 中的**接口契约**（路径、参数、响应结构）与代码是否一致
   - 如 D017：DD 定义 `monitoring_read`，代码用 `monitor_read` → 修代码对齐 DD

2. **设计文档需要更新吗？**
   - 如果设计文档**是正确的**，代码**是错的** → 修代码（如 D017）
   - 如果设计文档**有遗漏或错误** → 更新设计文档 + 修代码
   - 将决策记录在缺陷文件的「修复说明」中

3. **填写 `design_ref` 字段**: 在缺陷文件 frontmatter 中填写关联的设计章节引用
   - 格式示例: `design_ref: dd-user-mgmt §5.6, ad-global §4.2`
   - 便于后续追溯"哪些设计章节曾产生过缺陷"
4. **填写 `should_have_been_caught_by` 字段**:
   - 候选值至少包含: `spec`、`pd`、`ad`、`dd`、`plan`、`tasks`、`tests`、`review`、`smoke`
   - 如果一个缺陷暴露的是假成功、契约错位、路径漂移、异步状态机缺失等系统性问题，必须指出本应拦截它的阶段
   - 若现有规范无法拦截该缺陷，必须在修复说明中给出需要回灌到哪个命令/模板/规则

---

### Phase 6: 验证与闭环

> **来源**: 建议 6 — 缺陷闭环流程正式化

以下步骤全部 MUST 执行，缺一不可：

1. **运行全量测试**: `pytest tests/ -v --tb=short`，确认 0 失败（后端）
2. **前端构建验证**: `npm run build`（如涉及前端修改）
3. **回归测试**: 确认先前功能的测试仍然通过
4. **浏览器冒烟验证**（条件触发）: 当缺陷满足以下任一条件时，MUST 执行 `/speckit.smoke [相关页面]`：
   - `fix_ref` 中包含 `frontend/` 路径
   - `category` 为 `UI`
   - 缺陷现象描述涉及页面渲染、布局、交互
   - 验证范围: 仅冒烟修复涉及的页面（非全量），使用 `/speckit.smoke [page-path]`
5. **更新缺陷文件**:
   - 填写 `fix_ref`（修改了哪些文件）
   - 填写 `design_ref`（关联哪些设计章节）
   - 填写「修复说明」章节
   - 更新 `status` 为 `待确认`
6. **运行缺陷扫描**: `python scripts/scan_defects.py` 更新 INDEX.md
7. **建议 Code Review**: 对于 severity=严重 的缺陷，建议召唤 `code-reviewer` 子代理对修复代码进行审查

---

### Phase 7: 规范回灌

对每个已修复缺陷，MUST 额外完成以下判断:
1. 本缺陷原本最应该由哪个阶段拦住（填写 `should_have_been_caught_by`）
2. 当前规则/模板/命令是否已覆盖该模式；若未覆盖，必须登记回灌建议
3. 若属于高频模式（假成功、分页契约、异步状态机、下载返回形态等），优先沉淀到模板或命令层，而不是只停留在业务代码修复

## 缺陷文件规范

### 新增缺陷
- 复制 `specs/master/defects/_template.md`，重命名为 `D0xx.md`
- 截图放入 `specs/master/defects/images/`，命名 `D0xx-N.png`

### 缺陷文件 frontmatter 字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✅ | 缺陷编号 D001-D999 |
| `status` | ✅ | 新建/待理解/已理解/修复中/修复完成/待确认/重新打开/已确认/已关闭 |
| `category` | ✅ | 接口/UI/业务/规范/需求 |
| `severity` | | 严重/一般/轻微 |
| `priority` | | P1/P2/P3 |
| `created` | ✅ | 创建日期 YYYY-MM-DD |
| `reporter` | | 报告人 |
| `fix_ref` | | 修复涉及的文件路径（逗号分隔） |
| `design_ref` | | 关联的设计文档章节引用（如 `dd-user-mgmt §5.6`） |
| `should_have_been_caught_by` | | 本应拦截该缺陷的阶段（如 `tasks, tests, smoke`） |
| `related` | | 关联的用户故事/任务（自动或手动填写） |

### 状态流转

```
新建 → 待理解 → 已理解 → 修复中 → 修复完成 → 待确认 → 已确认 / 重新打开
                                                        ↗
                                          重新打开 → 修复中 ↩
```

## 输出格式

修复完成后，输出结构化报告：

```markdown
## 缺陷修复报告

### 1. 缺陷摘要
- ID / 标题 / 分类 / 严重程度
- 影响范围

### 2. 根因分析
- 根本原因
- 分类路由: 代码修复 / 设计补充 / 需求回溯

### 3. 修复概述
- 修改了哪些文件，做了什么
- 设计文档是否需要同步更新（Phase 5 结论）

### 4. 验证结果
- 测试通过情况
- 回归测试结果

### 5. 设计回溯
- 关联设计章节 (design_ref)
- 设计文档是否已同步更新

### 6. 潜在风险 & 后续建议
```

## 与其他命令的关系

```
/speckit.defects (本命令 — 缺陷全生命周期)
├── 扫描发现 → Phase 1
├── 分类路由 → Phase 2
│   ├── 代码修复 → Phase 3-6 (本命令内完成)
│   ├── 设计补充 → /speckit.design-dd → 补 tasks → /speckit.implement → 回到本命令
│   └── 需求回溯 → /speckit.specify 或 /speckit.design-pd → 重走设计链
├── 验证闭环 → Phase 6
└── 审查建议 → /speckit.review [fix]
```
