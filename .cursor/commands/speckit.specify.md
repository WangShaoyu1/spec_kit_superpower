# Speckit Specify - 需求澄清与规格定义

## 目的
将业务需求转化为结构化规格，产出 `spec.md`，作为后续 PD/AD/DD 的输入基线。

**核心规范**: `.specify/templates/spec-template.md` — spec.md 的结构和格式 MUST 遵循此模板。

## 执行流程

### Phase 1: 需求澄清
1. 读取用户提供的背景/需求描述
2. 识别核心利益相关者和用户角色
3. 梳理功能边界（在范围内 vs 不在范围内）
4. 若当前分支已存在 `spec / PD / AD / DD / plan` 草稿或历史产物，先做轻量冲突预检（FR 标签、模块 key、已知术语冲突），发现明显矛盾时先标记 `BLOCKER`

### Phase 2: 用户故事提取
- 按优先级排序（P1/MVP → P2 → P3）
- 每个故事包含：场景描述、验收场景（Given-When-Then）、独立测试点
- 明确故事间的依赖关系

### Phase 3: 功能需求定义
- 功能需求（FR-XXX）: 可验证的功能点
- 非功能需求: 性能、安全、可用性约束
- **每条 FR MUST 标注交付物类型标签**:
  - `[UI:<pd-module>]`: 后台 UI 功能, 需要 PD 交互设计
  - `[API]`: 纯 API / 服务端需求, 不需要 PD
  - `[Infra]`: 基础设施 / 非功能性需求, 不需要 PD
- UI 类 FR SHOULD 附加交互提示（`> 交互提示: ...`）

### Phase 4: 模块与交付物映射
- 根据 FR 标签, 汇总生成**模块与交付物映射表**
- 明确每个功能模块的交付物类型（后台 UI / API / 基础设施）
- 为 UI 模块分配 PD 模块 Key（小写 + 短横线, 如 `user-mgmt`）
- 纯 API / CLI / SDK 项目无 UI 模块时, 标注"无 UI 模块, 跳过 PD 阶段"

### Phase 4.5: 核心业务链路与真实成功信号
- 对每个 UI 模块定义 1-3 条"创建 / 执行 / 验证"闭环链路
- 为每条链路写明**真实成功信号**（真实数据、真实状态转换、真实结果），禁止以 toast、文案或 mock 值代替
- 若存在异步能力，提前定义"提交成功"与"业务成功"的差异，以及失败回传方式
- 若已知某些能力仅部分覆盖或依赖外部条件，必须显式登记为 `Deferred / Out of Scope / Blocked By`

### Phase 5: 成功标准
- 可量化的验收指标（SC-XXX）
- 技术约束和规模预估

## 输出产物

```yaml
# specs/{branch}/spec.md
---
version: 1.0
status: 已澄清
dependencies: []  # 依赖的其他 spec
---

# 1. 项目定位
# 2. 用户故事（按优先级）
# 3. 边界情况
# 4. 模块与交付物映射（新增: 为 PD 阶段提供模块拆分依据）
# 5. 功能需求（含 FR 标签 + 交互提示）
# 6. 成功标准
```

## 规格完整性检查清单

- [ ] 所有用户故事都有验收场景（Given-When-Then）
- [ ] 功能需求可追溯到用户故事
- [ ] **每条 FR 都标注了交付物类型标签**（`[UI:xxx]` / `[API]` / `[Infra]`）
- [ ] **UI 类 FR 附加了交互提示**（至少关键 FR）
- [ ] **模块与交付物映射表已创建**, 覆盖所有 FR
- [ ] 每个 UI 模块都定义了 1-3 条核心业务链路与真实成功信号
- [ ] 已显式记录 Deferred / Out of Scope / Blocked By，不把“部分覆盖”藏在备注里
- [ ] 边界情况覆盖异常路径
- [ ] 成功标准可量化验证
- [ ] 成功标准包含反假成功约束（异步结果、真实统计、真实进度）
- [ ] 关键术语已定义（实体/状态/角色）

## 下一步
spec.md 完成后，**必须**进入 `/speckit.design-pd`（产品交互设计）阶段，而非直接到模块 plan。
PD 阶段将基于模块映射表, 按 `pd-template.md` 规范为每个 UI 模块生成交互原型。
