## 概述

1. **设置**: 从仓库根目录运行 `.specify/scripts/powershell/check-prerequisites.ps1 -Json` 并解析 FEATURE_DIR 和 AVAILABLE_DOCS 列表. 所有路径必须是绝对路径.

2. **执行 pre-flight 文档冲突扫描**（生成任务前强制）:
   - 检查同一 FR 在 `spec / AD / DD` 中是否存在冲突口径
   - 检查 `AD` 引用的 PD 页面/流程是否真实存在
   - 检查 `plan.md` 中的源码路径是否与当前工程目录一致
   - 检查 `PD README` 中的“部分覆盖 / 待补充 / 待确认”是否已经在 `plan.md` 中显式承接
   - 检查每个 UI 模块是否已经定义 1-3 条核心业务链路与真实成功信号
   - 扫描结果必须分级输出:
     - `BLOCKER`: 必须先修设计文档, **不得继续生成 tasks**
     - `WARNING`: 允许继续, 但必须在对应任务文件中显式带风险提示与未完成声明
     - `INFO`: 仅记录

3. **加载设计文档**: 从 FEATURE_DIR 读取:
   - **必需**: pd-all/(产品交互设计 — 任务分解的**首要驱动源**，定义具体的页面、交互流程、状态变化)
   - **必需**: ad/(架构设计 — API 契约、数据流), dd/(详细设计 — 数据模型、状态机、算法、错误码)
   - **必需**: plan.md(阶段规划、技术栈、项目结构)
   - **参考**: spec.md(用户故事优先级 P1/P2/P3 + FR 标签 — 用于优先级排序和追溯)
   - 注意: ad/ 和 dd/ 可能是文件夹（含 README.md + 模块文件）或单文件（ad.md / dd.md）. 按实际结构加载.

4. **执行任务生成流程**:
   - **加载 pd-all/ 并按模块提取页面、交互流程、状态矩阵** — 这是任务拆分的首要来源
   - 加载 ad/(或 ad.md): 提取 API 端点 → 映射到 PD 模块
   - 加载 dd/(或 dd.md): 提取实体、状态机、算法 → 映射到 PD 模块
   - 加载 plan.md 并提取技术栈、阶段规划、项目结构
   - 加载 spec.md 提取用户故事优先级(P1/P2/P3) → 用于 PD 模块的排序参考
   - 加载 `plan.md` / `spec.md` 中的核心业务链路、真实成功信号、显式未完成声明
   - **按 PD 模块拆分生成独立的任务文件**:
     - `tasks/tasks-infra.md` — 设置 + 基础设施（阻塞所有模块）
     - `tasks/tasks-<module>.md` — 每个 PD 模块一个独立文件
     - `tasks/tasks-refinement.md` — 横切关注点 + 完善
     - `tasks/README.md` — 索引（模块列表、任务统计、依赖关系、执行策略）

5. **每个模块任务文件的内部结构**（TDD 模式，测试先行）:
   对于每个 PD 模块，按以下顺序生成任务:
   - **测试任务**（必须先于实现，确保 TDD）:
     - 契约测试: 覆盖 AD 定义的该模块全部 API 端点
     - 集成测试: 覆盖 AD 数据流中的关键路径
     - 消费契约测试: 覆盖前端真实请求字段、分页结构、下载/数组/对象返回形态
     - 状态机测试: 覆盖异步链路的提交中/处理中/成功/失败
     - E2E 测试: 覆盖 PD 交互原型中的关键用户操作路径
   - **后端任务**:
     - 数据模型/迁移: 来自 DD 实体定义
     - 服务层/算法: 来自 DD 算法伪代码
     - API 端点: 来自 AD 接口契约
   - **前端任务**:
     - 页面/组件: 来自 PD 交互原型
     - 状态管理: 来自 PD 状态矩阵
     - API 对接: 连接前后端
   - **模块检查点**: 对照 PD 交互稿验证
   - **显式未完成声明区**: 将 `Deferred / Stub / Out of Scope / Blocked By` 单独列出, 不得混在备注里
   - 应用任务规则: 
     - 不同文件 = 标记 [P] 表示并行
     - 相同文件 = 顺序执行(无 [P])
     - 测试**必须**在对应实现之前(TDD)
   - 每个模块文件内按顺序编号(T001、T002...)

6. **生成 tasks/README.md 索引**:
   - 全局统计: 总文件数、总任务数、各模块任务数
   - 模块执行顺序表: 模块名、优先级、任务数、依赖关系、状态
   - 跨模块依赖关系图
   - 执行策略(串行/并行模式)
   - 进度追踪: 各模块完成百分比（**必须由勾选状态自动汇总**, 不得手写）
   - 未完成声明汇总: 模块级 `Deferred / Stub / Out of Scope / Blocked By`

7. **报告**: 输出生成的 tasks/ 目录路径和摘要:
   - 生成了多少个文件
   - 总任务数
   - 每个 PD 模块的任务数(测试/后端/前端分类统计)
   - 建议的 MVP 范围
   - Pre-flight 扫描结果（BLOCKER/WARNING/INFO）
   - 每个模块的核心业务链路数量

任务生成上下文: $ARGUMENTS

每个任务必须足够具体, 以便 LLM 子代理可以在没有额外上下文的情况下完成它.

## 任务生成规则

**TDD 强制**: 每个功能模块**必须**包含测试任务. 测试先于实现编写, 确保在实施前测试失败(红灯), 实施后测试通过(绿灯).

**关键**: 任务按 **PD 模块**拆分为独立文件, 每个模块可独立实施和测试. PD 交互稿定义了具体的页面和交互流程, 是任务可拆分、可测试、可验证的直接依据.

**PD UI 逐项 Checklist 强制**: 每个前端页面任务（`[F-PAGE]`）MUST 附带 PD UI Checklist，列出该页面 PD 交互稿中定义的所有 UI 元素。Checklist 是该任务的验收标准。

> **来源**: PD 功能缺失根因分析（D031-D036）— 任务以「页面级」为粒度，未逐项枚举 PD UI 元素，
> 导致实现者凭个人理解选择性实现，遗漏统计卡、筛选器、表格列、操作按钮等。

**Checklist 格式示例**:

```markdown
- T032: [F-PAGE] 指令库列表页
  PD UI Checklist (pd-intent-library/index.html):
  - [ ] 统计卡: 总库数 / 已发布 / 训练中 / 即将满额
  - [ ] 表格列: 名称, Key, 语言, 意图数, 状态, 模型数量, 置信度阈值, 创建时间
  - [ ] 筛选器: 搜索框, 语言筛选, 状态筛选
  - [ ] 按钮: 新建指令库, 导入, 查询, 重置
  - [ ] 操作: 详情, 编辑, 删除
```

> **设计链路**: spec.md → PD → AD → DD → plan → **tasks/**
> spec.md 提供用户故事优先级用于排序参考; PD 提供具体的可实现单元.

**核心业务链路强制**:
- 每个 UI 模块 MUST 从 `plan.md` 继承 1-3 条核心业务链路
- 每条核心链路 MUST 至少拆出一项集成测试或 E2E 测试, 且验证最终结果而非仅验证入口步骤
- 未定义核心业务链路的模块不得生成"可完成"的任务集

**显式未完成声明强制**:
- `Deferred / Stub / Out of Scope / Blocked By` MUST 独立成节
- 任何写入该区的事项都不得再被计入完成率
- 若某能力为 `Stub`, 任务中 MUST 写明返回 `501` 或显式 `NotImplementedError`

### 任务来源映射

1. **来自 PD（产品交互设计）** - **首要驱动源**:
   - 每个 PD 模块 → 一个独立的 `tasks/tasks-<module>.md` 文件
   - PD 页面/交互流程 → 前端页面任务 + E2E 测试任务
   - PD 状态矩阵 → 前端状态管理任务 + 边界条件测试
   - **PD 统计卡/筛选器/表格列/按钮** → `[F-PAGE]` 任务的 PD UI Checklist（逐项列出，每项对应验收标准）

2. **来自 AD（架构设计）**:
   - API 端点 → 后端 API 任务 + 契约测试任务
   - 数据流图 → 集成测试任务

3. **来自 DD（详细设计）**:
   - 实体定义 → 数据模型/迁移任务
   - 算法伪代码 → 服务层任务 + 单元测试任务
   - 状态机 → 服务层任务 + 状态转移测试
   - 错误码 → 错误处理任务 + 异常场景测试

4. **基础设施**:
   - 共享基础设施 → `tasks/tasks-infra.md`
   - 跨模块共享实体(dd-global) → `tasks/tasks-infra.md` 基础阶段

### 模块内任务排序（TDD 顺序）

```
测试(红灯) → 模型 → 服务 → API端点 → 前端页面 → 集成验证(绿灯)
```

**前端任务的额外要求**:
- 每个 `[F-PAGE]` 任务 MUST 读取对应的 PD HTML 文件，提取所有 UI 元素
- 任务描述中 MUST 包含 PD UI Checklist（统计卡 × N、表格列 × N、筛选器 × N、按钮 × N）
- 子代理完成任务后，指挥官 MUST 逐项核对 Checklist，未勾选项视为未完成
- 若页面涉及真实数据消费，MUST 同时生成消费契约测试或联调检查项

### 输出目录结构

```
specs/{branch}/tasks/
├── README.md                    # 索引(模块列表/统计/依赖/策略/进度)
├── tasks-infra.md               # 设置 + 基础设施
├── tasks-<module-1>.md          # PD 模块 1 的全部任务
├── tasks-<module-2>.md          # PD 模块 2 的全部任务
├── ...
└── tasks-refinement.md          # 横切关注点 + 完善
```

## 垂直切片规则 [MUST]

任务执行 MUST 按垂直切片组织，严禁水平铺面。

### 切片定义
一个垂直切片 = 一条完整的业务链路，包含：测试(红灯) + 后端模型 + 后端服务 + 后端API + 前端页面 + 测试(绿灯)

### 切片顺序
- 切片 1（CRUD 基础）MUST 全部完成并通过集成测试后，才能开始切片 2
- 核心业务链路（训练/推理/评估等）MUST 作为独立切片，不得与 CRUD 混合
- 前端页面切片 MUST 在对应的后端切片完成后才能开始

### 示例（指令库模块）
```
切片 1: 库 CRUD (后端+测试) → 验证通过
切片 2: 数据集 + 意图 CRUD (后端+测试) → 验证通过
切片 3: 训练链路 (训练服务+API+集成测试) → 验证通过
切片 4: 推理链路 (推理服务+API+集成测试) → 验证通过
切片 5: 评估链路 (评估服务+API+集成测试) → 验证通过
切片 6: 前端全部页面 → E2E 通过
```

### 禁止行为
- ❌ 先写完所有 ORM 模型，再写所有服务，再写所有 API，再写所有前端
- ❌ 用"status 更新"冒充"真实业务逻辑实现"
- ❌ 跳过集成测试任务（T007/T008 等）直接写前端
- ✅ 一个切片做透做完，集成测试通过后，再开下一个切片
